# 《闽游蛙》载体选型备忘

> 版本：v1.0
> 日期：2026-10-08
> 用途：`闽游蛙-开发实施计划.md` 中 **D1（载体：小程序 vs 小游戏）** 的决策依据留档，也是 M0-T01 的输入材料
> 与规划书的关系：规划书 §1 已给出选型结论，本文补上**平台限制的实际核数**与两套预案的技术细节
> 事实核查方式：本文所有平台限制数字均来自官方文档或官方口径来源，非凭记忆；标注了来源与需复核项

---

## 0. 结论先行

**默认走路线 A：微信小程序（原生框架 + TDesign）。**

触发切换的条件、以及切换的真实代价，见 §5。**不必现在纠结，但必须在 M0 拿到类目结论后立刻确认。**

---

## 1. 平台限制（本次核实结果）

| 项 | 路线 A · 微信小程序 | 路线 B · 微信小游戏 |
|---|---|---|
| **单个主包/分包上限** | **2MB** | 主包 **4MB** |
| **总量上限** | 所有分包合计 **30MB**（服务商代开发的小程序为 20MB） | 主包 + 全部分包合计 **20MB** |
| 单个普通分包 | ≤ 2MB | 不限制单包大小（受 20MB 总量约束） |
| 独立分包 | ≤ 2MB | ≤ 4MB |
| **渲染层** | WXML / WXSS（WebView，或 Skyline） | **Canvas 全自绘；无 DOM、无 HTML、无 WXML** |
| 可用 UI 组件库 | TDesign Miniprogram、Vant Weapp 等 | **无**（界面元素全部自己绘制） |
| **类目** | 可自选，但需与功能实质相符 | **一级类目锁定「游戏」，不可更改** |
| 好友关系链 | **不可获取**（无对应 API） | 开放数据域内可用 `wx.getFriendCloudStorage` |
| 软著 | 需要（游戏类内容上线通常要求） | 提审时**强制**要求上传软著证书 |
| 内购 | 需版号，个人主体无法开通虚拟支付 | 同左 |
| 分享跳转 | 可创建分享卡片，可指向独立分包 | 可指定独立分包 `root` 作为分享入口 |

**来源**：
- 小程序分包限制：微信开放文档《分包加载》——"整个小程序所有分包大小不超过 30M（服务商代开发的小程序不超过 20M）；单个分包/主包大小不能超过 2M"
- 小游戏分包限制：腾讯云文档《小游戏分包加载》——"整个小游戏所有主包+分包大小不超过 20M；主包不超过 4M；单个普通分包不限制大小；单个独立分包不超过 4M"
- 好友关系链：微信开放文档小游戏 API `wx.getFriendCloudStorage`——"**只在开放数据域下可用**"，需 `scope.WxFriendInteraction` 授权，基础库 1.9.92+

> ⚠️ 上一版实施计划里写"小程序总包 20MB"是**错的**，已修正为 30MB。M0 仍需以官方最新文档复核一次。

### 1.1 一个容易误解的点

**小游戏的主包额度（4MB）比小程序（2MB）大，但这不构成选小游戏的理由。** 因为小游戏没有 WXML/WXSS，界面必须全部画出来——省下的 2MB 包体额度，要用几倍的开发工作量去换。

## 2. 路线 A：小程序有哪些开发方式

| 方式 | 技术栈 | 适合 | 评价 |
|---|---|---|---|
| **原生框架 + 组件库** | WXML / WXSS / JS(TS) + TDesign Miniprogram | 只发微信、追求最稳、组件现成 | **本项目推荐** |
| Taro | React 语法 → 编译到多端 | 需要同时发支付宝/抖音小程序 | 多端是唯一理由，否则多一层编译与坑 |
| uni-app | Vue 语法 → 编译到多端 | 团队是 Vue 背景（本项目后台是 Vue3） | 同上；若未来确需多端可考虑 |
| web-view 内嵌 H5 | H5 全套 | —— | **不推荐**：个人主体不可用 web-view，且体验割裂、无法调小程序原生能力 |

对本项目的额外说明：玩法逻辑层（`core/`）计划写成**不依赖 `wx.*` 的纯函数状态机**，所以即使将来从原生框架换到 Taro，逻辑层同样可以整体搬运——这是先天的解耦收益。

---

## 3. 路线 B：小游戏有哪些引擎

| 引擎 | 语言 | 引擎体积 | 优势 | 劣势 / 适用边界 |
|---|---|---|---|---|
| **Cocos Creator** | TypeScript | 约 700KB（可模块裁剪） | 微信小游戏市场占有率最高；2D/3D 兼顾；AssetBundle 分包体系成熟；构建面板把微信当一等目标 | 从零做微信小游戏时的**默认选择** |
| LayaAir | TS / JS / AS3 | 核心约 300KB | 轻量；DrawCall 合批效率高，3D 性能强 | 引擎运行时不像 Cocos 那样可复用微信客户端内置插件，需占自己的包体预算 |
| Unity + 微信转换 SDK | C# | 很大 | 官方转换工具，2025 年中起支持一键导出 | **只适合移植已有 Unity 项目**，从零做会死在 4MB 首包上 |
| 团结引擎（Unity 中国） | C# | 大 | 把微信小游戏当**原生构建目标**（非 WebGL 转换），基于 Unity 2022 LTS | 适合有 Unity 积累、且长期押注国内市场的团队 |
| 裸 Canvas / weapp-adapter | JS | 极小 | 最轻、最可控；若已有 Three.js 代码可复用 | 精灵系统、动画、碰撞、UI 全部自己实现 |
| ~~Egret（白鹭）~~ | TS | 小 | 老牌 2D，龙骨动画完善 | 社区活跃度持续下降，**新项目不建议** |

> 📌 **Cocos 的一个结构性优势（待复核）**：有资料提到自微信客户端 7.0.7 起，Cocos 引擎运行时被内置为微信 App 的插件——若玩家此前跑过任意 Cocos 小游戏，引擎代码已在本地，不占你的 4MB 预算。
> 这一条来自第三方指南，**未经官方文档确认**，M0 若进入预案 B 需优先复核。如果成立，它会显著影响引擎选择。

## 4. 为什么本项目判定走路线 A

不是"小程序更好"，而是**这个产品的形态与两条路线的能力恰好错配**：

| # | 判定依据 | 说明 |
|---|---|---|
| 1 | **工作量 90% 在 UI，不在渲染** | 产品是"看卡片、收东西、翻图鉴、看结算"。列表、网格、弹窗、Tab、大段文案排版——这些在 WXML 里是现成组件，在 Canvas 里要自己实现文本换行、滚动、点击命中、布局。用游戏引擎等于**先重写一套 UI 框架**，再写游戏 |
| 2 | **没有实时动画需求** | 玩法是"玩家零操作、蛙自主出行"，状态推进靠**时间戳解锁**，不存在帧循环。Canvas 的核心优势（每帧渲染）在这里完全用不上 |
| 3 | **现有技术栈无游戏引擎经验** | 团队是 Spring Boot + Vue3 + Flutter。Cocos 的学习成本是实打实的工期，且与现有可复用资产无关 |
| 4 | **类目弹性** | 小游戏一级类目**锁定「游戏」不可更改**，选了就没有退路（还需面对实名/防沉迷）；选 A 至少还能以"福建文旅内容产品"定位提交（规划书 §9.1 预案 A） |
| 5 | **后端复用** | 云开发下的逻辑与集合结构可平滑对接遇光后端；小游戏则要多做一层适配 |

### 4.1 必须承认的代价

走路线 A 有一个**确定的损失**：

> **拿不到微信好友关系链。** `wx.getFriendCloudStorage` 是**小游戏专属**且只能在开放数据域内调用；普通小程序没有任何等价 API。

后果：闽游蛙的好友系统只能靠「分享链接互加 + 蛙友码」，无法一键导入"也在玩的好友"。这会明显拖慢社交关系的冷启动。

缓解思路（已写进实施计划 A2 / D9）：
1. 分享落地页做成**独立分包**，被分享者无需下载主包即可打开，并在落地页放"成为蛙友"入口——把分享转化路径压到最短；
2. 用"互赠特产 + 看好友图鉴"作为社交动机（内容驱动），而不是靠关系链自动导入；
3. 把"好友规模"从核心玩法的必要前提，降级为**可选增强**——单机也能完整玩。

## 5. 迁移预案：什么情况下切路线 B

| 触发条件 | 动作 |
|---|---|
| M0 类目验证结论为「必须走游戏类目」 | 启动预案 B，技术栈切小游戏 |
| 后续运营中被平台要求补游戏类目 | 同上，但代价更大（已上线） |

### 5.1 切到路线 B 的真实代价（必须提前知道）

| 项 | 代价 |
|---|---|
| 渲染层 | **全部重写**，WXML/WXSS 代码不可复用；TDesign 依赖全部作废 |
| 页面骨架 | 从"页面路由 + 组件"改为"场景 + 节点树"，导航逻辑重写 |
| 后端 | 云函数与集合结构**可复用**（这部分不浪费） |
| 玩法逻辑 | **可复用**——前提是严格守住"`core/` 不 import `wx.*`"的铁律 |
| 工期 | M1 的 3 周不成立，需额外加入引擎学习与 UI 重写；建议整体上浮 30–50% |
| 引擎选型 | 从零做 → Cocos Creator（不要用 Unity 转换路线） |
| 意外收益 | 好友关系链可用（开放数据域），社交模块反而变简单 |

### 5.2 现在就要做的准备（成本极低，收益极大）

1. **严守实施计划 §3.1 的铁律 2**：`core/` 目录下任何文件不得 `import wx.*`。用 ESLint 规则强制拦截。
   → 这条规则的唯一目的，就是让上面那张表的"玩法逻辑可复用"成立。
2. **明信片插画按"独立资源 + 配置表 id 驱动"组织**，不写死在页面里。渲染层换掉时，美术资产与配置表零改动。
3. **别提前引入小程序特有的耦合**：例如不要在 `store` 里直接调 `wx.cloud`，统一走 `services/request` 适配层——这正是规划书 §4.4 建议"做适配层"的原因。

## 附录 · 一句话速查

- **做"游戏化的小程序"** → 原生框架 + TDesign，主包 2MB，总 30MB，类目自选
- **做"微信小游戏"** → Cocos Creator，主包 4MB，总 20MB，类目锁定游戏
- **两者的分界线不在"好不好玩"，而在"界面要不要自己画"**
