## 0. 这份文件补的是哪一块

| | 规划书 v0.1 | **实施计划 v1.0（本文）** |
|---|---|---|
| 回答的问题 | 做什么、做成什么样（产品定义） | 谁、按什么顺序、在多长时间内、做到什么程度算完 |

| 验收 | "能自己玩 5 分钟不崩" | 可机械复现的检查方式（脚本/数据断言/操作步骤） |

**当前项目状态**：计划阶段，**尚未开始编码**，Git 仓库未初始化，`apps/` 代码目录未创建。

**本文的执行原则**：
1. **先冻结接口，再并行开发**。前端与后端不同步开工的前提是契约先定（见 §3.5）。
2. **一条垂直切片跑通，胜过十个页面铺开**。M1 只做「行囊 → 出门 → 结算 → 明信片」这一条链，但要做完整。
3. **每个技术点必须给出验收方式**，不接受"看起来没问题"。
4. **未定项不阻塞已定项**。用默认假设先行，假设被推翻时按 §9 的影响面回溯。

## 1. 计划成立的前提（3 个必须先钉死的变量）

这三个变量直接决定排期，但当前未知。下文一律采用**默认假设**推进，你确认后我按实际值重算。

| 变量 | 默认假设 | 影响 | 需要你提供 |
|---|---|---|---|
| **答辩锚点日期** | 未定 → 全文按「相对周」排期 | 所有里程碑的绝对日期 | 竞赛答辩日 D |
| **人力规模与角色** | **3 人**（A 前端/小程序 + PM、B 后端/云函数 + 数据、C 美术/内容） | 并行轨道数量、工期系数 | 实际人数与分工 |
| **美术产能来源** | AI 辅助出稿 + 人工修（规划书 §10-4 的建议） | 最大工期风险项 | 画师是自有还是外包 |

### 1.1 倒排公式（拿到答辩日 D 后直接套）

规划书 §8 六阶段合计 **17 周**（含 M0）。答辩前留 **2 周缓冲**（提审驳回重提、真机适配返工）。

```
M0 开始日 = D − 133 天（约 19 周）
```

| 里程碑 | 相对周 | 反向锚点 |
|---|---|---|
| M0 立项与验证 | 第 1 周 | D − 133 |
| M1 核心可玩原型 | 第 2–4 周 | D − 126 |
| M2 系统完整版 | 第 5–8 周 | D − 105 |
| M3 内容填充 | 第 8–11 周 | D − 84 |
| M4 社交与运营 | 第 12–14 周 | D − 63 |
| M5 打磨与提审 | 第 15–17 周 | D − 42 |
| 缓冲（不入计划） | 第 18–19 周 | D − 21 → **答辩** |

### 1.2 人力换算系数

| 实际人力 | 换算 |
|---|---|
| 1 人全栈 | M0/M1 周期 ×2.5（做不快，因为要串行）；M2–M5 各 ×2 |
| 3 人（默认） | 按本文排期直接执行 |
| ≥5 人 | 可把 M3 内容填充与 M2 系统开发**完全并行**，总工期压到 13 周 |

> 人力不足时**优先砍内容量，不砍技术债**（幂等、时间权威、分包这三件事砍掉后期修不回来）。

## 2. 尚未确定的功能模块

这是本次补强的第一块。分三类：**A 规划书完全没提但必须有**、**B 提了但边界模糊**、**C 明确不做**。

### 2.1 A 类：规划书未覆盖、但必须有（新增模块）

| # | 模块 | 为什么必须有 | 归属 | 优先级 |
|---|---|---|---|---|
| A1 | **订阅消息与唤回** | 放置类玩法的**留存命脉**。蛙回家的那一刻不通知玩家，次日留存会掉一大截。规划书全文未提 | M2 | P0 |
| A2 | **好友关系链建立方式** | 技术空白：小程序**拿不到微信好友列表**（`wx.getFriendCloudStorage` 只在小游戏开放数据域可用）。规划书 §4.1 有「好友页」，但没说好友从哪来 | M2（打底）/ M4（放量） | P0 |
| A3 | **天气系统** | 规划书 §2.3 道具表里「油纸伞：雨天照常出行」「雨天专属明信片」，以及 §2.4 `areaPool = 权重(道具) ∩ 权重(季节/天气)` —— 都依赖天气，但**天气从哪来**从未定义 | M2 | P0 |
| A4 | **成就与任务的具体定义** | §4.1 有 `pages/quests`，但无成就表、无日常任务的类型定义（且要注意 §2.1 原则「没有每日任务强制打卡」，两者需调和） | M3 | P1 |
| A5 | **庭院装扮 / 外观系统** | §3.3 提到「解锁专属庭院装扮」「庭院春节装扮」，但无模块承载 | M4 | P1 |
| A6 | **配置管理后台** | §4.6 要求"所有数值走配置表"，但**谁改？怎么改？** 让策划直接改云数据库控制台风险高（无校验、无版本、无回滚） | M2 | P0 |
| A7 | **埋点与数据看板** | 竞赛答辩需要"数据证明"，且内容调优依赖漏斗数据（首次出门转化、结算完播率、明信片收集率） | M2 | P1 |
| A8 | **被分享者视角的落地页** | §5.3 设计了分享，但**分享出去对方看到什么**未定义。这是分享转化率的关键（建议独立分包承载，见 §4.6） | M4 | P1 |
| A9 | **运营位 / 公告 / 客服入口** | 提审硬要求：小程序需有客服入口；运营需要公告位（活动、维护通知） | M5 | P1 |
| A10 | **错误监控与日志** | 无监控则线上问题只能靠用户口头反馈。竞赛演示现场崩一次就完了 | M2 | P0 |

### 2.2 B 类：规划书提了，但边界模糊（需补充定义）

| # | 模块 | 模糊点 | 本文件的处理 |
|---|---|---|---|
| B1 | **访客系统** | §3.2 给了 7 个访客的「到访条件/招待偏好/回礼」，但**行为流程**未定义：访客何时出现、停留多久、招待几次、拒绝招待会怎样 | §3.3 补充状态与流程，M2 实现 |
| B2 | **图鉴四册的边界** | §4.1 写「目的地/明信片/特产/美食」四册，但**美食 vs 特产重叠**（沙县拌面既是特产也是食物） | §3.3 给出去重规则：食物册 = 食材/小吃原型；特产册 = 可带回的伴手礼 |
| B3 | **杂货铺「出售特产」** | 特产可卖三叶草，但**回收价与获取难度的关系**未定，容易变成"刷钱路径" | 归入 M3 经济平衡任务（M3-T07） |
| B4 | **明信片"传说级不可重复获得"** | 与"图鉴计数 `count`"字段矛盾（不可重复却又计数） | §3.3 裁定：传说不计重复；`count` 仅对普通/稀有有意义 |
| B5 | **首次引导的 3 步内容** | §5.1 只说"3 步教学" | M1-T14 定义并实现 |
| B6 | **音效触发点清单** | §3.4 只给了风格方向 | M3-T09 输出触发表 |

### 2.3 C 类：本期明确**不做**（防止范围蔓延）

写下来是为了在开发中被问到"要不要加"时有据可依。

| 不做 | 原因 |
|---|---|
| 虚拟商品内购 | 开内购即需版号；个人主体也无法开通（规划书 §9.1） |
| 对战 / 排行榜 | 与"低压力"核心体验冲突，且增加合规面 |
| 用户 UGC 留言 | 需接入内容安全审核，成本大于收益（§9.3） |
| 微信好友关系链导入 | 小程序平台不开放该能力（见 A2） |
| 实时联机 | 无玩法需求 |
| 真实地图底图 | 用风格化手绘地图替代（§9.4） |
| 账号密码 / 手机号登录 | 强制索权会被驳回（§5.1） |
| iOS 端虚拟支付 | 平台规则限制 + 本作无内购 |
| 全站 Skyline 迁移 | 见 §4.7，只在 M5 对单页做灰度评估 |

## 3. 模块边界与职责

### 3.1 分层架构

```
┌──────────────────────────────────────────────────────────────┐
│  视图层 (WXML/WXSS)                                           │
│  pages/  ·  components/  ·  subpackages/                      │
│  职责：只做渲染与用户手势。禁止出现任何数值计算与概率逻辑        │
└───────────────────────────┬──────────────────────────────────┘
                            │ 只读 data（由 store 注入）
┌───────────────────────────▼──────────────────────────────────┐
│  状态层 (store/, mobx-miniprogram)                            │
│  单一数据源：user / frog / bag / collection / config          │
│  职责：持有快照、派发 action、驱动 setData                      │
└───────────────────────────┬──────────────────────────────────┘
                            │ 调用
┌───────────────────────────▼──────────────────────────────────┐
│  领域层 (core/) —— 纯函数，无 wx.* 依赖，可被 Jest 直接测      │
│  travelEngine / frogMachine / collection / economy / config    │
│  职责：状态推导、剧本解析、图鉴判定、经济换算                   │
└───────────────────────────┬──────────────────────────────────┘
                            │ services/request（适配层）
┌───────────────────────────▼──────────────────────────────────┐
│  接入层 (services/)                                            │
│  request(云函数调用) · storage · audio · share · track         │
│  职责：屏蔽平台差异、超时重试、降级、埋点                       │
└───────────────────────────┬──────────────────────────────────┘
                            │ wx.cloud.callFunction
┌───────────────────────────▼──────────────────────────────────┐
│  云端 (cloud/functions) —— 唯一权威                            │
│  云函数：login / travelStart / travelSettle / harvestClover …  │
└───────────────────────────┬──────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────┐
│  数据层：云数据库（唯一权威）+ 云存储(图片) + configs(只读配置) │
└──────────────────────────────────────────────────────────────┘
```

**三条不可越界的铁律**：

1. **视图层不得算数**。WXML 里出现 `{{a * b}}` 这类运算是 review 必拒项 —— 数值一律在 `core/` 算好放进 `data`。
2. **`core/` 不得 import `wx.*`**。这是它可被 Jest 直测、且未来能整体搬到小游戏的前提（规划书 §1 的迁移预案依赖这条）。
3. **前端不得产生权威数据**。三叶草、背包、图鉴的每一次写入，最终都以云端返回值为准；前端的乐观更新只是"临时显示"。

#### 3.2.3 领域层（core/）—— 本项目技术核心

| 模块 | 职责 | 输出 |
|---|---|---|
| `core/frogMachine` | 由 `(journey, userFlags, now)` **推导**蛙状态 | `FrogState` + 可选 action 列表 |
| `core/travelEngine` | 解析服务端剧本：给定 `now`，产出"已解锁 / 已到达 / 未解锁"三段视图 | `JourneyView` |
| `core/collection` | 图鉴解锁判定、去重、收集度计算 | `CollectionStats` |
| `core/economy` | 食物档位 → 时长区间、道具 → 权重影响说明文本、售价换算 | 只读推导 |
| `core/config` | 配置表校验与归一化（补齐默认值、校验引用完整性） | `ConfigBundle` |
| `core/time` | 时长人性化展示（"还有 3 小时 12 分"）、服务端时间偏移换算 | 纯函数 |

> `core/` 的每个模块必须能在 Node 里裸跑（无 `wx`），这是 M1 单测的前提。

#### 3.2.4 接入层（services/）

| 模块 | 职责 | 关键点 |
|---|---|---|
| `services/request` | 云函数调用统一入口 | 超时（8s）、指数退避重试（2 次）、幂等键透传、降级返回 |
| `services/clock` | 服务端时间权威 | 维护 `offset = serverTime − Date.now()`，冷启动重算（§4.2） |
| `services/storage` | 本地缓存封装 | 命名空间 `myw:`、版本迁移、容量保护（超限驱逐非关键 key） |
| `services/audio` | 音效管理 | 实例池复用，`onHide` 暂停（小程序音频不自动停） |
| `services/share` | 分享卡片生成 | 携带 `shareToken`；**不绑任何奖励** |
| `services/track` | 埋点上报 | 批量攒包（10 条或 5s）、失败丢弃不阻塞 |
| `services/subscribe` | 订阅消息授权 | 见 §4.8，只在特定时点调用 |

### 3.4 数据所有权矩阵（谁能写哪个集合）

**只有一个写者**是防脏数据最有效的手段。任何"两个地方都能写同一字段"的设计，在弱网下必然冲突。

| 集合 | 唯一写者 | 前端可写？ | 备注 |
|---|---|---|---|
| `users` | `login` / `bagMutate` | ❌ | `settings` 字段例外（本地优先，异步同步） |
| `frogs` | `travelStart` / `travelSettle` | ❌ | 前端只读展示 |

## 4. 关键技术实现思路

每个技术点给 **问题 → 方案 → 落地要点 → 验收方式**。验收方式一律是**可机械复现**的。

### 4.1 确定性随机引擎（跨端可复现）

**问题**：规划书 §2.4 要求"用 seed 生成确定性随机序列"，但没定算法。若用 `Math.random()` 或不可移植的 PRNG，会导致：无法审计产出是否被篡改、未来遇光 Java 端想复用算不出来、服务端换语言后老数据无法复现。

**方案**：选用**整数位运算型 PRNG**（xorshift32 / mulberry32），只用 `^ << >> + *` 与 32 位溢出，不使用浮点累积。

```js
// core/random.js —— 建议实现（Node / 小程序 / 云函数三端同码）
function xorshift32(seed) {
  let x = seed | 0;
  if (x === 0) x = 0x9e3779b9 | 0;   // 0 是吸收态，需兜底
  return function next() {
    x ^= x << 13; x |= 0;
    x ^= x >>> 17; x |= 0;
    x ^= x << 5;  x |= 0;
    return (x >>> 0) / 4294967296;   // [0, 1)
  };
}

// 种子：FNV-1a 32 位
function seedOf(openid, departAt, salt) {
  const s = `${openid}|${departAt}|${salt}`;
  let h = 0x811c9dc5 | 0;
  for (let i = 0; i < s.length; i++) {
    h ^= s.charCodeAt(i);
    h = Math.imul(h, 0x01000193) | 0;
  }
  return h;
}
```

**落地要点**：
1. **`salt` 必须落库**（存进 `journeys.salt`）。否则事后无法用同一把钥匙复现，审计就失去意义。
2. **加权抽取写成独立纯函数**，输入 `(prng, pool[{id, weight}])`，输出 `id`。所有抽卡（目的地、事件、明信片）**共用同一个 prng 实例**，按固定顺序消费随机数 —— 顺序即协议，改动顺序等于改动历史数据。
3. 云函数用 Node 跑，与前端同码；`Math.imul` 在 Java 里可手写等价实现，故该算法**可移植到遇光 Spring Boot**。

**验收方式**：
> 写一段脚本，固定 `(openid='test', departAt=1730000000000, salt='abc')`，连续产出 1000 个随机数，计算 `SHA256(序列)`。分别在 **Node 本地**与**云函数环境**跑，两个哈希必须逐字符相同。同时跑 100 次完整剧本生成，产出的 `destId` 序列必须每次都一致。

### 4.2 时间权威与时钟偏移校正

**问题**：用户改手机时间就能跳过等待 —— 这是放置类游戏最常见的破解点（规划书 §6.4 已列为风险）。但**前端又必须显示倒计时**，不能每次问服务端。

**方案**：**服务端时间权威 + 客户端偏移量校正**。

```js
// services/clock.js
let offset = 0;                       // 服务端时间 - 本地时间
function sync(serverTime) { offset = serverTime - Date.now(); }
function now() { return Date.now() + offset; }   // 以此替代裸 Date.now()
```

**落地要点**：
1. `login` / `travelStart` 等所有云函数**都返回 `serverTime`**，每次收到就重算 `offset`（防止长时间漂移）。
2. 前端**所有时间判断走 `clock.now()`**，禁止裸调 `Date.now()`（加 ESLint 规则 `no-restricted-globals` 拦截）。
3. **状态推导的结果只用于展示**。蛙是否真的回来了，以云端 `frogs.state` 为准；前端算出来"该回来了"时，主动调 `travelSettle` 并**以返回值覆盖本地**。
4. 冷启动时若 `offset` 未知（首启或缓存被清），先渲染本地快照，拿到 `serverTime` 后刷新。

**验收方式**：
> 手动把手机系统时间 ±24 小时、±7 天，重启小程序。断言：① 归期倒计时显示不变；② 三叶草生长量不变；③ 无法通过改时间触发结算。

### 4.3 纯函数状态机（状态可推导，不存中间态）

**问题**：规划书 §2.2 定义了 6 个状态。若把"当前状态"当作一个存储字段，玩家离线期间状态不会自己推进（数据库里的值冻结），回来就出错。

**方案**：**状态由事实推导，不作为独立字段存储**。

```js
// core/frogMachine.js —— 纯函数
function deriveFrogState({ journey, settled, visitor, now }) {
  if (journey && !settled) {
    if (now < journey.expectReturnAt) return 'TRAVELING';
    if (now < journey.expectReturnAt + RETURN_WINDOW_MS) return 'RETURNING';
    return 'SETTLING';                    // 到点未结算 → 等玩家参与
  }
  if (visitor && visitor.expireAt > now) return 'VISITOR_AT_HOME';
  return 'IDLE_HOME';
}
```

**关键裁定**：
- `SETTLING` **不能只由时间推导**，必须由服务端事实 `journey.settled === false` 决定。理由：结算需要玩家参与（"逐条揭示"是核心体验，§5.4），离线期间这个状态必须**保留**，不能自动跳过。
- 有 `VISITOR_AT_HOME` 时，**访客可并行存在**，不覆盖 `IDLE_HOME`（庭院里可以有蛙又有客）。
- `PACKING` 是**纯前端 3 秒过场动画**，不落库（否则中途杀进程会卡在 PACKING）。

**存储的只有事实**：`journey`（云端权威）、`settled` 标记、`visitor.expireAt`。状态永远是算出来的。

**验收方式**：
> 用 Jest 遍历 `now` 的 6 个关键区间边界（`expectReturnAt−1ms`、`+0ms`、`+RETURN_WINDOW−1ms`、`+RETURN_WINDOW`、`settled=true` 各组组合），断言输出状态符合状态转移表；**断言不存在"从任意状态出发 3 步内回到 IDLE_HOME"之外的死循环**（对应规划书 §7 的"状态机无死状态"）。

### 4.4 事务与幂等（三条写路径）

**问题**：弱网重试、用户连点、多端并发，都会导致重复扣库存 / 重复领奖 / 库存为负。

**方案**：**确定性 `_id` + 事务内先读后写 + 状态标记二次校验**。

| 写路径 | 幂等手段 | 具体做法 |
|---|---|---|
| `travelStart` | 前端生成 `requestId`，**用它构造 journey `_id`** | `_id = ${openid}_${requestId}`。重复请求会撞 `_id`，写入失败 → 直接返回已存在的 journey（幂等返回）。**注意**：先做"是否已有未结算 journey"的前置校验，避免用户真的开第二段旅程 |
| `travelSettle` | `journeyId` 天然唯一 | 事务内 `doc(journeyId).get()` → 校验 `settled === false` → 写入背包/图鉴 → 置 `settled = true`。若读到 `true`，直接返回已结算结果（幂等返回，不报错） |
| `giftClaim` | `giftId` | 事务内校验 `status === 'PENDING'` 再改 `CLAIMED` |

**落地要点**：
1. **云开发事务的限制要提前确认**：事务内一般只能用 `doc()` 按 `_id` 访问单条记录，**不支持 `where` 查询与聚合**。因此所有需要条件判断的写操作，都要设计成"能按 `_id` 定位"的形状 —— 这就是为什么上面用"确定性 `_id`"而不是"where 查询"。
   > 该限制以官方最新文档为准，M0 需实测确认（列入 M0-T05）。
2. **不用前端传来的库存**。`travelStart` 事务内自己读 `bags`、自己校验、自己扣减。
3. **幂等返回不报错**。重复调用返回与首次相同的结果体，前端逻辑统一。

**验收方式**：
> 写一个并发测试脚本，对同一 `journeyId` **并发调用 `travelSettle` 10 次**。断言：① `journeys.settled` 只由 `false` 变为 `true` 一次；② `user_postcards` 的 `count` 总增量 = 首次返回的产出数，不多不少；③ 三叶草只加一次。
> 另测库存为负：把食物数量设为 0 再调 `travelStart`，断言返回错误码而非创建 journey。

### 4.5 配置热更新

**问题**：小程序每次改数值都要走审核（1–3 天）。策划调一次平衡卡 3 天，迭代无法进行。

**方案**：**`configs` 集合 + 版本号比对 + 本地兜底 JSON**。

```
启动 → 读本地 myw:config（含 version）
     → callFunction('readConfig', { version })
     → 服务端比对：相同 → { changed: false }（省流量）
                    不同 → { changed: true, version, data }
     → 前端校验 schema → 写本地 → 刷新 store
失败或超时 → 用本地兜底 JSON（随包发布，保证首启永远有数据）
```

**落地要点**：
1. **单文档大小**：云开发单文档上限约 512KB，但**建议单条控制在 128KB 以内**，超出则按区/册拆分（如 `destinations:mindong`、`destinations:minnan`）。列出各配置表的预估条目数与体积。
2. **版本号即资源版本**：`configs.version` 同时驱动图片 CDN 路径（`postcards/{id}@{version}.webp`），保证"改了配置就一定拿到新图"，不会因缓存错配。
3. **前端必须做 schema 校验**（`core/config`）。云端配置写错会让所有用户崩，兜底 JSON 是最后一道防线。
4. **配置表的引用完整性**：`destinations.postcardIds` 引用的明信片必须存在。用一个"配置校验脚本"在 `adminConfig` 写入前跑一遍（A6 模块的一部分）。

**验收方式**：
> 改 `configs` 里某明信片的文案 → 提升 `version` → 杀掉小程序重进。断言新文案出现，**且未发版、未提审**。再把配置故意写坏（引用不存在的 `postcardId`），断言前台降级到本地兜底 JSON 且不崩。

### 4.6 包体与分包策略

**问题**：小程序主包/单个分包上限 **2MB**，所有分包合计上限 **30MB**（服务商代开发为 20MB）。60+ 明信片插画、7 个访客、四大图鉴册，直接铺进去必然超限。

> 平台限制的核数结果与来源见 `闽游蛙-载体选型备忘.md` §1。

**方案**：

| 包 | 内容 | 体积预算 |
|---|---|---|
| **主包** | 庭院、行囊、杂货铺、旅途中、明信片详情、我的、首启引导、`core/`、`services/`、`store/` | **≤ 1.5MB**（留 0.5MB 余量） |
| 分包 A `collection` | 图鉴四册 | ≤ 2MB |
| 分包 B `social` | 好友、访客、赠礼 | ≤ 2MB |
| 分包 C `growth` | 任务与成就 | ≤ 2MB |
| **独立分包** `landing` | **分享落地页** | ≤ 1MB |

**落地要点**：
1. **图片一律不进包**：全部走云存储 + CDN，`webp` 格式，明信片插画按"列表缩略图 / 详情大图"两套尺寸交付（列表 ≤ 80KB，详情 ≤ 300KB）。
2. **`landing` 做成独立分包**（`"independent": true`）。被分享者点开时**无需下载主包**即可看到落地页 —— 这是分享转化率的关键优化，否则流量在加载主包时就流失了。
3. **预下载策略**：在庭院页 `onReady` 后 `wx.loadSubpackage` 预下载 `collection`（最高频的二级页）。
4. **`app.json` 声明** `requiredPrivateInfos`（定位，见 §4.9）与 `requiredBackgroundModes`（本作不需要，保持空）。
5. 每完成一个里程碑跑一次包体检查，**任一包超预算即视为该里程碑未达成**。

**验收方式**：
> 微信开发者工具的「代码依赖分析 / 包体积」视图导出各包体积；断言主包 ≤1.5MB、各分包 ≤2MB、所有分包合计 ≤30MB。截图存档。

### 4.7 渲染选型（WebView vs Skyline）与列表性能

**问题**：Skyline 动画能力更强，但组件库兼容性、生态成熟度需评估；TDesign 部分组件基于 WebView 特性。

**方案**：**默认 WebView + TDesign，Skyline 只做单页灰度评估。**

| 页面 | 渲染方案 | 理由 |
|---|---|---|
| 全站（M1–M4） | WebView + TDesign | 生态成熟，组件齐全，省 60% 样式工作量（规划书 §4.2） |
| 庭院页动画 | 当前用 CSS animation / sprite 序列帧 | 交互轻，无需 worklet |
| 明信片墙（60+ 项） | **分页加载 + `IntersectionObserver` 懒加载** | 不做一次性渲染 |
| M5 灰度评估 | 仅在「庭院」单页试验 Skyline | 若收益显著（首屏渲染 < 800ms）再考虑扩展 |

**落地要点**：
1. **setData 纪律**（每个 setData 都跨 JS→Native 桥）：
   - 合并更新：多个字段一次 `setData`，不连调多次。
   - 路径更新：改单个 SKU 用 `this.setData({ 'bag.items': newItems })` 而非整个 `bag`。
   - **只传视图需要的字段**（规划书 §2.4 的"最小 setData 负载"原则要落到 code review checklist）。
   - 长列表单次 `setData` 数据量控制在 **< 256KB**。
2. **不把大对象放进 `data`**：配置表全量（可能 100KB+）放 `store`/模块闭包，只把当前页需要的切片放进 `data`。
3. **骨架屏 + 本地快照秒开**：先用 `myw:*` 缓存渲染，云端数据异步刷新（规划书 §9.6 的冷启动对策）。

**验收方式**：
> 开发者工具「体验评分」+ 真机（中端安卓）实测：① 首屏渲染 < 1.5s（M5 目标 <2s 是底线）；② 庭院页单次会话 `setData` 调用次数与总负载量（用 Performance 面板导出）；③ 明信片墙滚动帧率无持续掉帧。

### 4.8 订阅消息与唤回（A1，留存命脉）

**问题**：放置类玩法的核心是"离开—回来"。玩家不知道蛙回来了，就会彻底忘记这个产品。

**方案**：**一次性订阅消息，在高意愿时点反复请求授权。**

| 项 | 内容 |
|---|---|
| 模板 | ① "你的蛙旅行回来了，带了东西给你" ② "有客人在门口等你" |
| 请求时点 | **① 点"送出门"成功后**（此时玩家对归期最有期待）；**② 结算完成时**（为下一次出门做铺垫） |
| 发送方 | 云函数 `subscribeSend`，在 `travelStart` 时按 `expectReturnAt` 注册定时触发；结算后立即发"归来"消息 |
| 平台限制 | 一次性订阅 **一次授权只能发一条**；Android 支持"总是保持"，iOS 每次都要用户点 |

**落地要点**：
1. **模板申请要提前**：模板 ID 需在微信公众平台申请，有审核周期 → **M0 就提交（M0-T06）**，否则 M2 无法联调。
2. **不要在冷启动弹授权**。用户还没进入情境就弹订阅，拒绝率高且体验差（规划书 §5.1 要求首启零授权）。
3. **请求要"说明用途"**：弹之前给一个自定义的说明卡片（"开启提醒，蛙回家第一时间告诉你"），让用户知道为什么点。
4. 发送失败要容错：用户已拒绝或额度用尽时静默跳过，**不要报错中断主流程**。

**验收方式**：
> 真机操作：送出门 → 弹订阅授权 → 同意 → 用测试工具把 `expectReturnAt` 改为当前时间 + 1 分钟 → 等待定时触发 → 断言收到订阅消息，且点击后**正确跳转到庭院页**（`page` 路径带参数需测试）。

### 4.9 手绘地图与定位合规

**问题**：规划书 §3.1 要"八闽地图 + 点位点亮"，§9.4 要求地图合规（只能用腾讯/高德/百度/天地图，领土要素必须合规）。真实底图合规成本高、且视觉上与手绘水彩调性冲突。

**方案**（规划书已建议，此处给落地细节）：**游戏内地图形制为风格化手绘地图，不接真实底图。**

| 场景 | 方案 |
|---|---|
| 图鉴里的「八闽地图」 | **手绘插画底图 + 绝对定位锚点**。锚点坐标由策划在配置表里给"手绘图上的百分比坐标"（`x: 0-100, y: 0-100`），**完全不用真实经纬度** |
| 点位点亮 | 已访问目的地 → 显示彩色 2D 卡通图标；未访问 → 灰色剪影 |
| 真实定位（若做"线下打卡"） | 仅此功能接**腾讯地图 SDK**（GCJ-02），`wx.getLocation` 需在 `app.json` 的 `requiredPrivateInfos` 声明 + 后台申请开通 |
| 用户坐标 | **只存本地**，不上传、不聚合、不公开（PIPL 要求，规划书 §9.4） |

**落地要点**：
1. 手绘地图底图尺寸建议 750×900 逻辑像素的等比放大图（2x/3x），锚点用百分比定位以适配不同机型。
2. 若**本期不做线下打卡**，则**完全不申请定位权限** —— 少一个权限就少一个提审风险点。建议 M1–M3 不接定位，M4 再评估。
3. 地图上的地名标注**必须与官方行政区划一致**；中国台湾/中国香港/中国澳门的表述必须规范（规划书 §9.5）。

**验收方式**：
> ① 在不同分辨率机型（iPhone SE / 中端安卓 / iPad）截图，断言锚点相对位置一致（按百分比校验坐标为同一比例）；② 全局检索代码，断言无 `wx.getLocation`（本期不做打卡时）→ 用 grep 检查。

### 4.10 本地缓存与迁移

**方案**：按规划书 §6.2 的 7 个 key，加一层 `services/storage`。

**落地要点**：
1. **容量保护**：写入前预检 `wx.getStorageInfoSync()`，接近上限时按优先级驱逐：`myw:config` > `myw:collection` > 其余（配置可从云端重拉，图鉴需重建但与云端一致）。
2. **迁移函数**：`migrations[1→2](old) → new`，`onLaunch` 里按 `myw:v` 顺序执行。**迁移函数永不删除**，因为老用户可能跨多个版本升级。
3. **云端结构只增字段、不改语义**（规划书 §6.5）。需要改语义时新增字段 + 双写过渡。

**验收方式**：
> 造一个 v1 结构的 `myw:*` 缓存 → 用当前版本启动 → 断言迁移后结构为最新且关键数据（图鉴 id 列表）无丢失。

## 5. 任务拆分方式

### 5.1 拆分规则（先定规则，再拆任务）

| 规则 | 说明 |
|---|---|
| **颗粒度** | 单个任务 **≤ 2 人日**。超过就继续拆 —— 这是"能被领取"的前提 |
| **编号** | `M{里程碑}-T{两位序号}`，例如 `M1-T03`。编号一经分配不复用 |
| **每个任务必须写清** | ① 交付物（哪个文件/哪个页面）② 依赖（被谁阻塞）③ DoD（怎么算完成，可复现） |

| **技术债不可延期** | 幂等、时间权威、分包预算 —— 这三件事当期不做，后期修不回来，必须写进 M1/M2 |
| **验收模板** | 「打开 X → 执行 Y → 看到 Z → 断言 W」四段式，避免"功能正常"这类无法证伪的描述 |
