## 0. 一句话定位

> 玩家养一只住在福建的蛙。为它准备行囊，它自主出游，从八闽各地寄回明信片与特产。

**游戏类型**：放置收集 / 轻度养成（无需操作的"等待型"内容产品）
**平台**：微信小程序
**目标用户**：18–35 岁；对福建有情感联结（本地人 / 在闽就读 / 计划来闽旅行）的人群
**单次时长**：30–60 秒，日均 2–3 次
**核心体验三感**：
- **低压力** —— 没有失败、没有体力条、没有每日任务强制打卡
- **惊喜感** —— 蛙去哪、寄回什么，玩家无法完全控制
- **地域认同** —— "我家的蛙替我去看了我家门口的那座塔"

**与「遇光」的关系**：闽游蛙 = 虚拟种草层（看见福建）→ 遇光 = 真实行程层（去到福建）。两者共用一套福建 POI 内容资产，这是竞品无法复制的护城河。

## 1. 载体选型（第一个必须拍板的决策）

| | 方案 A：微信小程序（原生页面） | 方案 B：微信小游戏（Canvas） |
|---|---|---|
| 渲染 | WXML/WXSS 页面 + CSS 动画 | Canvas 全自绘 |
| 开发效率 | 高（可用 TDesign 组件库，列表/卡片/弹窗全是现成） | 低（UI 要自己画） |
| 类目 | 一级类目可自选（风险点，见 §9） | 一级类目锁定为"游戏" |
| 变现 | 广告为主 | 广告 + 官方 IAA 激励分成政策 |
| 与遇光复用 | 高（可共用后端接口与用户体系） | 低（逻辑层需重写，只有数据可用） |
| 动画表现力 | 中（够用） | 高 |

**建议：选方案 A。**
理由：本作玩法是"看卡片、收东西、翻图鉴"，交互全部是按钮与列表，几乎没有实时动画需求；小程序在开发效率、组件复用、团队现有技术栈（Spring Boot + Vue3 + Flutter）上都占优。把玩法逻辑层写成纯函数状态机（不依赖渲染层），未来若确需迁小游戏，逻辑可整体搬运。

> ⚠️ 但方案 A 有一个必须在 M0 验证的假设：**平台是否会把本产品判定为"游戏"并要求对应类目**。详见 §9.1。这是全项目最大的单点风险，先验证再写代码。

## 2. 核心玩法设计

### 2.1 核心循环

```
   ┌─ 准备行囊（放食物 + 放道具）────────────────────┐
   │                                                │
   ▼                                                │
蛙自主出门 ──► 旅途中（离线推进 / 玩家零操作）        │
                   │                                │
                   ├─► 寄回明信片（可收藏）           │
                   ├─► 寄回特产（可收集/送人）        │
                   └─► 遇到访客或剧情事件             │
                   │                                │
                   ▼                                │
              回家结算：收明信片 / 收特产 / 触发图鉴解锁 ─┘
                   │
                   └─► 三叶草产出、图鉴进度、成就达成
```

关键设计原则（忠于《旅行青蛙》的"不可控感"）：
1. **玩家不能决定目的地**，只能通过道具与食物"影响概率"
2. **玩家不能催促**青蛙回家（不设计"召回"按钮）
3. **玩家不能失败**，最差的结果只是"这次带回来的东西比较普通"

### 2.2 蛙的状态机

```
IDLE_HOME ──(玩家点了"送出门")──► PACKING ──► TRAVELING ──► RETURNING ──► SETTLING ──► IDLE_HOME
                                                     │
                                                     └─ 条件触发：POSTCARD_ARRIVED（明信片到达，不打断主状态）
IDLE_HOME 期间的旁支状态：VISITOR_AT_HOME（有访客，可招待）
```

| 状态 | 含义 | 关键字段 | 前端表现 |
|---|---|---|---|
| `IDLE_HOME` | 蛙在家 | `state, homeSince` | 庭院里能看到蛙，可操作行囊 |
| `PACKING` | 打包中 | `packSnapshot` | 3 秒动画（给玩家"我做了准备"的仪式感） |
| `TRAVELING` | 旅途中 | `departAt, expectReturnAt` | 庭院空着（可放一封信在桌上） |
| `RETURNING` | 归途中 | `returnAt` | 门口出现影子，次日可见 |
| `SETTLING` | 结算中 | — | 一次性弹出结算面板，逐个揭示 |
| `VISITOR_AT_HOME` | 有客来访 | `visitorId, expireAt` | 门口坐着另一只蛙，可拖动食物招待 |

**为什么要 `SETTLING` 独立成态**：结算涉及"图鉴解锁 + 成就判定 + 背包写入 + 云端回写"，如果跟 `IDLE_HOME` 合并，容易在弱网下出现"物品收了两次"或"图鉴没点亮"。独立成态后可用一个事务化云函数收口，失败可重试。

### 2.3 资源与经济

只设 **一种货币：三叶草**。原生玩法中蛙吃三叶草，本作沿用，让玩家"照顾蛙的日常"和"买旅行物资"形成同一套资源循环。

| 资源 | 来源 | 去向 |
|---|---|---|
| 三叶草 | 庭院随时间自然生长（上限内可采）；访客赠礼；看广告翻倍 | 买食物、买道具 |
| 食物（消耗品） | 杂货铺购买、访客赠送 | 决定旅行**时长档位**与"幸运值" |
| 道具（装备，不消耗） | 杂货铺购买、图鉴解锁赠送 | 决定**目的地权重**与**稀有明信片权重** |
| 特产 | 旅行带回 | 收藏图鉴 / 赠送好友 / 出售换三叶草 |
| 明信片 | 旅行带回 | 收藏图鉴 / 分享展示（分享不给奖励，见 §9.3） |

**食物档位设计**（食物越"大菜"，出门越久、越远）：

| 档位 | 代表食物 | 时长 | 到达区域 |
|---|---|---|---|
| 轻食 | 光饼、锅边糊 | 2–4 h | 本市周边 |
| 家常 | 面线糊、四果汤、沙县拌面 | 6–12 h | 本区（如闽南区内） |
| 硬菜 | 沙茶面、烧肉粽、客家酿豆腐 | 12–24 h | 跨区 |
| 大菜 | 佛跳墙、姜母鸭、白斩河田鸡 | 24–48 h | 全省任意，稀有目的地权重提升 |

**道具权重设计**（道具影响"去哪"，不保证去哪）：

| 道具 | 原型出处 | 效果 |
|---|---|---|
| 油纸伞 | 福州传统工艺 | 雨天照常出行；雨天专属明信片解锁 |
| 惠安女斗笠 | 泉州惠安女服饰 | 海边目的地权重 ↑ |
| 竹编食盒 | 客家竹编 | 步行/古道类目的地权重 ↑ |
| 茶篓 | 安溪茶农 | 茶园类目的地（安溪、武夷山）权重 ↑ |
| 帆布画板 | 通用写生道具 | 摄影/写生类明信片（霞浦滩涂、武夷云海）权重 ↑ |
| 簪花围 | 泉州蟳埔女习俗 | 泉州全域权重 ↑↑；触发"簪花围"限定剧情 |
| 建盏 | 南平建阳建窑 | 茶事剧情与"点茶"类明信片 |
| 提线木偶挂饰 | 泉州提线木偶戏 | 触发泉州非遗类剧情 |
| 南音琵琶挂饰 | 泉州南音 | 触发泉州夜巷类剧情 |
| 平潭风筝 | 平潭岛 | 滨海目的地权重 ↑ |

> 数值细节（具体权重、概率、上限）属于 GDD 第 3 章内容，计划阶段只需定"影响什么维度"。

### 2.4 旅行结算模型（技术核心）

**核心决策：服务端权威 + 一次性预生成整段旅程。**

```
玩家点"送出门"
  → 云函数 travelStart()
      ├ 校验三叶草/食物/道具库存
      ├ 扣减库存（事务）
      ├ 用 seed = hash(openid + departAt + 随机盐) 生成确定性随机序列
      ├ 逐节点推导：目的地 → 时长 → 事件序列 → 明信片 → 特产
      └ 写入 journeys 集合，状态置 TRAVELING
前端只负责"按时间戳逐条解锁展示"，不做任何数值计算
```

**为什么必须服务端权威**：
- 玩家改本地时间会直接作弊（原生玩法最容易被破解的点）
- 换设备后旅程必须能续上
- 明信片图鉴是核心收集品，一旦可伪造，收集的意义就没了

**事件推导规则（示例）**：
```
duration      = baseDuration(food.tier) × 道具时长修正 × (0.85 ~ 1.15)
areaPool      = 权重(道具) ∩ 权重(季节/天气)
destId        = 从 areaPool 加权抽取
eventCount    = clamp(round(duration / 6h), 1, 6)
for each event: 触发条件 → 候选池 → 加权抽取 → 产出(postcard | specialty | 剧情)
postcardProb  = 基础概率 + 道具加成 + 图鉴未收集补偿（保底机制）
```
**保底机制很关键**：如果某个目的地的明信片连续 N 次没抽到，第 N+1 次强制命中。否则玩家会因挫败感流失。

### 2.5 明信片的三种稀有度

| 稀有度 | 获取方式 | 视觉 |
|---|---|---|
| 普通 | 单纯到达目的地 | 单幅插画 + 邮戳 |
| 稀有 | 需要特定道具 / 特定季节 | 加烫金边 + 蛙穿着特色服饰 |
| 传说 | 需要多重条件（道具 + 节庆 + 天气 + 概率） | 多帧手绘小漫（3–4 格），且不可重复获得 |

### 3.4 美术与音频风格

- **画风**：手绘水彩 + 低饱和闽南色（红砖厝赭红、靛蓝、抹茶绿、月白）
- **蛙的造型**：本体不变，靠"服饰道具"变化体现地域性（簪花围、惠安女斗笠、畲族凤凰装）
- **明信片**：插画 + 手写体邮戳 + 手写祝福语，允许玩家长按保存到相册（这是天然的分享动机，且不违反诱导分享规则）
- **音效**：南音、洞箫、木偶戏锣鼓采样；注意版权，建议原创或采购商用授权
- **版权红线**：地标实景照片有著作权，**建议全部插画化重绘**；不要使用网络图片、不要使用未授权字体（小程序内字体需可商用授权）

### 4.4 后端方案（二选一）

| | 云开发 CloudBase | 自建（复用遇光 Spring Boot） |
|---|---|---|
| 上手速度 | 快（无需服务器、无需备案域名） | 慢 |
| 与遇光打通 | 需额外做接口对接 | 直接复用 107 个 API 的用户体系 |
| 成本 | 按量付费，早期几乎免费 | 需服务器 + HTTPS 域名 |
| 适用 | 竞赛 Demo、MVP | 长期运营 |

**建议**：M1–M3 用云开发快速跑通，把 `services/request` 做成适配层，M4 之后若要打通遇光，只替换适配层实现，不动业务代码。

### 4.5 云函数清单

| 云函数 | 职责 | 关键点 |
|---|---|---|
| `login` | 换取 openid，建/取用户档 | 幂等 |
| `travelStart` | 生成整段旅程剧本 | 事务扣库存 + 服务端时间 |
| `travelSettle` | 结算、写背包、解锁图鉴 | 事务 + 幂等键，防重复领取 |
| `harvestClover` | 采三叶草 | 按服务端时间算生长量，防刷 |
| `friendVisit` | 访问好友庭院 | 每日次数限流 |
| `giftSend` / `giftClaim` | 赠礼 / 领礼 | 幂等，防重复领 |
| `readConfig` | 下发策划配置 | 支持热更新，免发版 |

### 4.6 配置化（重要）

**所有数值必须走配置表**（`destinations` / `foods` / `items` / `specialties` / `postcards` / `quests` / `events`），本地留一份兜底 JSON。
理由：小程序每次改数值都要走审核，策划调平衡迭代一次卡 1–3 天，配置热更新能把迭代周期压到分钟级。这是小程序游戏和原生 App 最大的工程差异。

## 5. 用户交互流程

### 5.1 首次进入
```
启动 → 匿名登录（拿 openid）→ 3 步引导（可跳过）→ 赠初始食物×2 + 初始道具×1
     → 庭院：蛙在家里打盹 → 引导点"行囊" → 放 1 份食物 → 点"送出门" → 蛙走出画面
     → 提示"它大约 X 小时后回来，也许会给你寄东西" → 退出
```
> 首次不要求任何授权（不用手机号、不用头像昵称）。审核规则要求核心功能必须支持免登录使用，强制索权会直接被驳回。

### 5.2 日常（单次 30 秒）
```
打开 → 庭院
  ├─ 蛙不在家：显示"旅途第 N 天" + 最新明信片入口 + 采三叶草
  ├─ 蛙在家：弹出结算面板（逐个揭示明信片与特产）→ 一键收下 → 补充行囊 → 再送出门
  └─ 有访客：门口坐着另一只蛙 → 拖动食物招待 → 收下回礼
```

### 5.3 社交流程（合规版）
```
明信片详情页 → 长按保存到相册 / 点击分享给好友（纯功能按钮，不绑奖励）
好友列表 → 进入好友庭院（只读）→ 赠送特产 → 好友下次打开收到
```
> ⚠️ **不能设计成"分享得三叶草""助力解锁"**。平台自 2026 年起已能识别变体文案，任何"分享 + 利益钩子"的组合都会被判定为诱导分享。替代方案：把社交动力放在"互赠特产"和"看好友的图鉴"上——这是内容驱动，不是奖励驱动。

### 5.4 关键交互细节
- 结算面板：**必须逐条揭示**（延迟 300–500ms 一条），一次性铺满会破坏惊喜感
- 三叶草：点击采集，配短音效与飘字
- 蛙出门：给 1–2 秒的"走出画面"动画，玩家要有"送别感"
- 弱网：所有写操作乐观更新 + 后台重试；失败时回滚并提示"稍后在'我的'里同步"

## 6. 数据持久化设计

### 6.1 三层存储

| 层 | 载体 | 定位 | 典型内容 |
|---|---|---|---|
| L1 本地缓存 | `wx.setStorageSync` | 首屏秒开、离线可看 | 蛙状态快照、背包快照、图鉴快照、配置缓存 |
| L2 云数据库 | 云开发数据库 | **唯一权威** | 用户、旅程、背包、图鉴、好友、礼物 |
| L3 配置表 | 云数据库（只读） | 策划热更新 | 目的地/食物/道具/特产/明信片/任务/节庆 |

> 小程序本地缓存有容量上限（官方约单 key 1MB、总量 10MB，**以官方最新文档为准**）。因此本地只缓存"渲染首屏需要的字段"，不做全量镜像；图片资源一律走 CDN/云存储 + 分包，不进本地缓存。

**冲突解决**：以 L2 为准。启动时拉取服务端档，与本地快照做"版本号比对"，服务端版本更新则覆盖本地。所有写操作先落 L2 再更新 L1。

### 6.2 本地存储 Key 规范

| Key | 内容 | 大小预算 |
|---|---|---|
| `myw:v` | schema 版本号（用于迁移） | < 100 B |
| `myw:user` | 昵称、头像、设置 | < 1 KB |
| `myw:frog` | 蛙状态快照（state、departAt、expectReturnAt） | < 1 KB |
| `myw:bag` | 背包快照（食物/道具/特产，仅 id + 数量） | < 8 KB |
| `myw:collection` | 图鉴快照（已解锁 id 数组） | < 16 KB |
| `myw:config` | 配置表缓存 + 版本号 | < 128 KB |
| `myw:settings` | 音效、震动、首次引导已完成标记 | < 500 B |

### 6.3 云数据库集合与字段

**users**
```
{ _id, _openid, nickName, avatarUrl, createdAt, lastActiveAt,
  clover: { count, lastHarvestAt },
  settings: { sound, haptic },
  schemaVersion }
```

**frogs**（每用户一条，与 users 分离便于高频更新）
```
{ _openid, state, homeSince, departAt, expectReturnAt,
  currentJourneyId, name, cosmetics: [itemId], updatedAt }
```

**journeys**（一次旅行一条）
```
{ _id, _openid, seed, status: 'TRAVELING'|'SETTLED',
  foodId, itemIds: [], departAt, expectReturnAt, settleAt,
  events: [ { seq, unlockAt, type: 'postcard'|'specialty'|'story',
              refId, revealed } ],
  producedPostcards: [], producedSpecialties: [],
  settled: false, idempotencyKey }
```

**bags**
```
{ _openid, food: { foodId: count }, items: { itemId: count },
  specialties: { specId: count }, updatedAt }
```

**user_postcards** / **user_destinations** / **user_specialties**（三张图鉴表）
```
user_postcards    { _openid, postcardId, firstGotAt, count, isNew }
user_destinations { _openid, destId, firstVisitAt, visitCount }
user_specialties  { _openid, specId, firstGotAt, count }
```

**friends** / **gifts**
```
friends { _openid, friendOpenid, since, lastVisitAt, dailyVisitCount }
gifts   { from, to, type: 'specialty'|'item', refId, count,
          status: 'PENDING'|'CLAIMED', createdAt, claimedAt, idempotencyKey }
```

**configs**（只读，按 `type + key` 组织，带 `version` 字段）

### 6.4 一致性、防作弊与幂等

| 风险 | 对策 |
|---|---|
| 玩家改本地时间 | 所有时间以服务端 `Date.now()` 为准；本地时间只用于倒计时动画 |
| 重复领结算奖励 | `travelSettle` 用 `idempotencyKey`（= journeyId）去重，`settled` 标记二次校验 |
| 重复领礼物 | `giftClaim` 事务内校验 `status === 'PENDING'` 再改为 `CLAIMED` |
| 刷三叶草 | 云函数按 `lastHarvestAt` 与服务端时间算生长量，单次采集封顶 |
| 库存为负 | `travelStart` 事务内"读—校验—写"，不用前端传的库存 |
| 换设备丢档 | 全部权威数据在 L2，L1 只是缓存，可随时重建 |

### 6.5 数据迁移

`myw:v` 存 schemaVersion。每次结构调整都写一条迁移函数（老版本 → 新版本），在 `onLaunch` 里跑一次。本地缓存可以丢，但**云端数据不能丢**，所以云端结构调整一律"只增字段、不改字段语义"。

## 7. 计划阶段应完成的 GDD 结构

计划阶段的目标不是"写完 GDD"，而是**把不确定性最高的三件事定下来**：玩法闭环能不能成立、平台类目能不能过、福建内容资产够不够撑 3 个月更新。

**GDD 目录与计划阶段交付标准**：

| 章 | 章节 | 计划阶段要产出 | 完成标准 |
|---|---|---|---|
| 1 | 项目概述 | 一句话定位、目标用户、核心三感、竞品拆解（旅行青蛙 3 页） | 能用一句话让外人听懂 |
| 2 | 玩法与系统 | 核心循环、状态机、经济模型 | 状态机无死状态，能画出闭环 |
| 3 | 数值设计 | 食物档位表、道具权重表、明信片概率表、保底规则 | 数值可调，且全在配置表 |
| 4 | 内容设计 | 五大区目的地库（≥30）、明信片清单（≥60）、食物（≥40）、特产（≥30）、访客（≥7）、剧情（≥10） | 清单条目有名有姓有出处 |
| 5 | 交互与界面 | 页面清单、流程图、关键页面线框、视觉规范（配色/字体/圆角） | 线框能直接进设计稿 |
| 6 | 技术与数据 | 架构图、集合 Schema、云函数清单、本地 Key 规范 | Schema 字段级可落库 |
| 7 | 合规与资质 | 类目方案、资质清单、诱导分享自查、地图合规、未成年保护 | 每条有结论和责任人 |
| 8 | 内容生产 | 美术资源清单与命名规范、音频清单、素材版权来源 | 每项素材有明确来源 |
| 9 | 里程碑与排期 | 阶段、交付物、验收标准、依赖 | 排到"哪周交什么" |
| 10 | 风险与对策 | 风险表（概率×影响×对策） | 高风险项有兜底方案 |
| 附 | 术语表 / 参考资料 | 地名与民俗的权威出处（地方志、非遗名录） | 编审时能自证 |

**计划阶段的硬门槛（做完才算进入 M1）**：
1. 核心循环能用纸面流程跑通 3 轮，无卡点
2. 类目方案有明确结论（见 §9.1）
3. 五大区目的地库填满，且每区至少 4 张明信片
4. 云数据库 Schema 冻结

## 8. 开发里程碑

> 以"相对周"给出。若以竞赛答辩日为锚点，请反推并倒排（答辩前 2 周必须进入 M5）。

| 里程碑 | 周期 | 交付物 | 验收标准（DoD） |
|---|---|---|---|
| **M0 立项与验证** | 第 1 周 | GDD v0.1、类目可行性结论、纸面原型、竞品拆解 | 类目有明确结论；核心循环纸面跑通 3 轮 |

| **M2 系统完整版** | 第 5–8 周 | 云开发接入、图鉴三册、杂货铺、访客、真实服务端结算 | 换设备档不丢；改时间不作弊；结算不重复 |

| **M4 社交与运营** | 第 12–14 周 | 好友互访、赠礼、节庆限时活动框架、成就系统 | 双人实测互赠成功；节庆可配置切换 |
| **M5 打磨与提审** | 第 15–17 周 | 性能优化、机型适配、合规自查清单、提审、灰度 | 首屏 < 2s；主包 < 2MB；合规清单全通过 |

**并行工作流**（不要串行做）：
- 美术资源从 M1 就要启动（插画是最大的工期风险，60 张明信片不可能在 M3 一周内画完）
- 合规与资质从 M0 就并行推进（备案有等待期）
- 软著登记建议 M1 就提交（有办理周期）

**里程碑之间不做"全量测试"**，只在 M2、M5 做两轮完整回归，其余阶段做冒烟测试。

## 9. 风险与合规

### 9.1 类目与资质（最高风险，M0 必须验证）

以 2026 年的平台规则为准，核心判断线是**有没有内购**，但有两点需要特别小心：

| 事项 | 当前规则要点 | 对本作的影响 |
|---|---|---|
| **软著** | 游戏类内容上线审核通常需要软件著作权登记 | **M1 就提交软著申请**，周期长，别拖到提审前 |
| **ICP 备案** | 所有境内运营的小程序都需完成工信部备案（经微信公众平台提交），免费但有几个工作日到数周的等待期 | M0 启动，别等 M5 |
| **版号（ISBN）** | **开内购就必须有版号**，无例外；纯广告变现（IAA）目前不需要。棋牌/捕鱼等品类无豁免。版号申请主体必须是企业，个人主体无资格 | 本作**规划为纯广告变现、不做内购**，可规避版号 |
| **个人主体限制** | 个人主体无法开通虚拟支付；可做的类目也受限 | 若团队是学生个人主体，广告变现是唯一路径 |
| **类目归属** | 平台按"功能实质"判定。"游戏化"的收集玩法是否必须走游戏类目，是本项目最大的不确定项 | **M0 用最小 Demo 提审验证，或直接咨询平台客服**；同时准备两套方案（见下） |

**两套预案**：
- **预案 A（推荐）**：以"福建文旅内容产品"定位提交，弱化"游戏"表述，功能描述聚焦"明信片收集 / 图鉴 / 好友互动"，按技术选型方案 A（原生小程序）实现。
- **预案 B**：如平台要求游戏类目 → 转微信小游戏，走一级"游戏"类目（不可更改），二级类目发布前可改、发布后锁定，需重新评估渲染层（用 Cocos 或原生 Canvas）。

> 这一项的结论直接决定技术方案，所以它是 M0 的第一件事，不是 M5 的收尾工作。

### 9.2 变现设计（合规约束下的方案）

| 方式 | 合规性 | 备注 |
|---|---|---|
| 激励视频广告（采三叶草翻倍、加速生长） | ✅ 推荐 | 主变现手段；广告位需与内容明显区分，关闭按钮要够大 |
| 插屏广告 | ⚠️ 谨慎 | 不得遮挡主要内容；单次会话曝光次数不宜过多 |
| 明信片保存到相册 | ✅ 推荐 | 天然分享动机，且不涉奖励 |
| **分享得奖励 / 助力解锁** | ❌ 禁止 | 会被判定为诱导分享 |
| 虚拟商品内购 | ❌ 本期不做 | 开内购即需版号；个人主体也无法开通 |
| 广告收入 | — | 小游戏有官方 IAA 激励分成政策（30 天/90 天梯度），**小程序与政策适用范围需 M0 核实** |

### 9.3 内容与运营红线

| 红线 | 具体要求 |
|---|---|
| 诱导分享 | 分享按钮不得与任何奖励绑定；文案不得含"转发得…""邀请…领…"等利益钩子 |
| 强制授权 | 不得强制索取手机号/定位/相册；核心功能必须免登录可用；权限在用到时动态申请并说明用途 |
| 未成年人保护 | 若被认定为游戏类，需接入实名与防沉迷；本作无消费、无对战，风险较低，但需保留监护人提示 |
| 社交内容 | 若开放好友间留言，需接内容安全审核（可用腾讯云内容安全） |
| 导航结构 | 底部 Tab ≤ 5 项，层级 ≤ 3 级，返回路径符合直觉 |

### 9.4 地图与定位合规

若实现"八闽地图 + 景区点位点亮"（含 GPS 地理围栏触发）：

| 项 | 要求 |
|---|---|
| 地图来源 | 只能用腾讯地图 / 高德 / 百度 / 天地图。**不得使用 Google Maps、Apple Maps、Mapbox、Leaflet + OpenStreetMap 等** |
| 推荐方案 | 腾讯地图（与微信同生态），坐标系用 GCJ-02 |
| 领土要素 | 国界、中国台湾、南海诸岛等要素必须符合国家标准，不得错绘、漏绘、错标；底图必须有合规审图号来源 |
| 敏感点位 | 不得标注军事禁区、涉密单位、未公开敏感坐标 |
| 个人位置 | 用户签到坐标只存本地私有存储，不上传、不公开、不聚合发布（个人信息保护法要求） |
| 权限申请 | `wx.getLocation` 等接口需在 `app.json` 的 `requiredPrivateInfos` 中声明，并在小程序管理后台申请开通；未申请会直接调用失败 |

> **建议**：游戏内的"地图"优先做成**风格化手绘八闽地图**（不做真实底图），只在"我去过这里"这类需要真实定位的功能上接入合规地图 SDK。这样既规避了底图合规风险，视觉上也更符合手绘水彩的整体调性。

### 9.5 素材与知识产权

| 项 | 对策 |
|---|---|
| 地标建筑实景 | 全部插画化重绘，不使用实景照片 |
| 字体 | 只用可商用授权字体（或系统字体） |
| 音乐音效 | 原创或采购商用授权；不要用网络"免费素材" |
| 地名与民俗表述 | 以地方志、非遗名录等权威来源为准；中国台湾/中国香港/中国澳门的表述必须规范 |
| 用户数据 | 遵守个人信息保护法；不收集非必要信息，不对外提供 |

### 9.6 技术风险

| 风险 | 影响 | 对策 |
|---|---|---|
| 插画产能不足 | M3 内容填充卡死 | M1 就启动美术；先做 12 张核心明信片，其余走"模板化插画"（同一构图换元素） |
| 包体超限 | 无法提审 | 主包 < 2MB；明信片资源走分包 + 云存储；用 webp |
| 服务端生成随机被质疑"不公平" | 玩家信任问题 | 公开"影响概率的道具说明"，让玩家知道道具的作用方向 |
| 云开发冷启动慢 | 首屏体验差 | 本地快照先渲染，云端数据异步刷新 |
