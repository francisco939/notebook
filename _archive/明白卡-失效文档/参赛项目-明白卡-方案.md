## 〇、与本地既有项目的边界

这是本方案的立项前提。工作区已有两条产品线，方案必须在**赛道、人群、场景、数据**四个维度上与它们零重叠。

| 维度 | 遇光（全栈旅行应用） | 闽游蛙（小程序游戏） | **明白卡（本项目）** |
|---|---|---|---|
| 赛道 | 文旅 / 旅行服务 | 休闲游戏 / 收集养成 | **信息无障碍 / 家庭照护工具** |
| 核心用户 | 来闽游客、旅行者 | 青年休闲玩家 | **隔代照护的祖辈家长（55–75 岁）** |
| 使用场景 | 出行前规划、在途导览 | 碎片时间放置游玩 | **家庭群里收到通知的那一刻** |
| 数据对象 | 景点、行程、文物、订单 | 明信片、特产、图鉴、蛙 | **群通知、行动项、期限、缴费** |
| AI 用法 | 景点讲解、行程推荐 | 无 | **多模态解构：非结构化文本 → 行动结构** |

**唯一共用的东西是工程基建**（微信云开发、TDesign 组件库、云函数结构），不涉及任何业务逻辑、数据模型或用户资产。三条线可以并行开发，不互相阻塞。

**边界再申明一遍**：本项目不做景点、不做文化展示、不做任何游戏化机制、不涉及收集与养成、不面向游客或玩家。

## 一、要解决的问题

### 1.1 问题的核心

微信已经成为中国家庭处理日常事务的**事实总线**。学校的活动通知、社区的告示、物业的提醒、缴费的安排，全都发在微信群里。

但这些信息是**纯文本加图片**，没有任何结构，并且会被群里的闲聊持续淹没。

对于一个熟悉智能手机的年轻人来说，这只是"翻回去找一下"的小麻烦。但对于**正在帮子女带孩子的祖辈家长**来说，一次群通知要独自完成五步：

1. **找到它** —— 通知夹在几十条闲聊之间
2. **读完它** —— 常常是几百字的长文，配三到五张图
3. **理解它** —— 通知体书面语（"届时请携带相关材料于指定时间前往"）
4. **记住它** —— 没有任何提醒机制，全靠脑子
5. **执行它** —— 交钱、带东西、按时到达

**每一步都会掉队，五步叠加，掉队几乎必然。**

### 1.2 掉队的真实代价

| 后果 | 具体表现 |
|---|---|
| 漏交钱 | 老师私聊催缴，老人尴尬，孩子受影响 |
| 漏带东西 | 孩子在学校被批评，老人自责 |
| 记错时间 | 白跑一趟，或错过活动 |
| **误信诈骗** | 班级群/家长群是冒充老师收费的高发地带，老人缺乏核验能力 |
| 不敢问 | 怕在群里被说"连这个都不会"，宁愿不问 |
| 子女被反复打扰 | 上班时间接到"老师说的那个是什么意思"的电话 |

### 1.3 一个被忽略的判断

**数字鸿沟的真正形态，不是"不会用手机"，而是"群里的话看不懂"。**

绝大多数助老产品在解决"怎么点、怎么滑、字太小"，也就是**操作层**的问题。但祖辈家长能熟练地发语音、抢红包、刷视频号——他们的操作能力没有问题。

他们卡住的地方是**信息层**：面对一段书面语的通知，无法在有限时间内完成"提取行动项"这个认知任务。

这是一个**尚未被产品化**的缺口。

## 二、目标用户与使用场景

### 2.1 目标用户

**核心用户：隔代照护中的祖辈家长**

| 特征 | 描述 |
|---|---|
| 年龄 | 55–75 岁 |
| 身份 | 正在协助子女照看学龄孙辈的爷爷奶奶、外公外婆 |
| 手机能力 | 会发语音、会看视频、会抢红包；不擅长文字阅读与信息管理 |
| 关键约束 | 视力下降（老花）、阅读速度慢、不敢在群里提问 |
| 所在场景 | 活跃在 1–3 个班级群 / 家长群中 |

**次要用户：在外务工或通勤的双职工父母**

他们需要远程掌握孩子学校的事务，但白天无法及时回应群里消息。他们是**触发者**——多数情况下，是子女帮父母完成首次配置。

**扩展用户（M3 阶段）**

独居老人：社区群里的通知、公告、防诈提醒，认知负荷问题完全同构。

> ⚠️ 待补充：隔代抚养家庭的规模数据。答辩前需引用国家统计局或权威人口研究的具体口径，本方案暂不列数字，避免使用无法溯源的估算。

### 2.2 使用场景

**场景 A · 一条长通知**

奶奶在三年二班家长群看到老师发的消息：一段文字说明秋游安排，外加三张图（活动流程表、需携带物品照片、一张缴费二维码）。

现在：她逐字读完，不确定"要不要交钱"、"交多少"、"什么时候交"，于是打电话问儿子。

明白卡：长按消息 → 转发给明白卡 → 得到一张行动卡。

```
秋游通知                              [读给我听]

1  交秋游费 200 元
   10 月 10 日（本周五）前

2  准备：雨衣、运动鞋、午餐
   10 月 12 日（周日）晚上装好

3  集合时间：10 月 13 日 早 7:30
   校门口

[打电话问孩子]
```

**场景 B · 一条可疑收费**

群里有人发："紧急通知：本学期教辅资料费 298 元，请各位家长今天内扫码支付，逾期影响孩子上课。"

现在：老人扫码，钱没了。

明白卡：

```
注意，这条要先确认                   [读给我听]

· 用了"今天内""逾期影响上课"这类催办话术
· 收款方式为个人收款码，不是学校对公账户
· 群里以往的通知都由老师本人发出，这条不是

建议：先打电话给老师本人核实
[一键拨给老师]  [拨给孩子]
```

> **必须说清的一点**：小程序无法读取聊天记录，也无法验证群成员的真实身份。风险提示是**基于通知内容特征的启发式判断**，不是身份认证。这个边界不能含糊，写进产品说明与答辩材料。

**场景 C · 子女端同步（M2）**

儿子在开会，手机收到一条摘要："母亲今天收到一条缴费通知，已确认是学校发出的，10 月 10 日前交 200 元。"他不需要打电话，也不需要事后被追问。

**场景 D · 回溯（M2）**

老人想问"上个月秋游要带什么"，不需要翻聊天记录，直接在班级档案里按时间翻。**不依赖关键词搜索**——老人记不住关键词。

## 三、创新亮点

### 亮点 1 · 不是"摘要"，是"解构"

市面上的 AI 摘要工具输出的是**更短的文字**。本产品输出的是**结构化的行动**。

这是两种不同的任务：

| | 文本摘要 | 行动解构（本产品） |
|---|---|---|
| 输出 | 一段话 | `{做什么, 何时前, 多少钱, 带什么, 谁的事}` |
| 假设 | 用户会读完 | 用户只看得懂短句 |
| 边界 | 任意文本 | 通知、告示、缴费提醒 |

AI 的任务是从一段混杂着客套话、背景说明、具体要求的长文中，**只抽出需要执行的部分**，并把相对时间（"本周五前"）解析成绝对日期。

### 亮点 2 · 界面为"认知负荷"设计，不是把普通 UI 放大

- 一屏**一张**卡，不滚动就能看完
- 每张卡最多 **3 条**行动项，多的折叠
- 全文支持**语音播报**——老花眼患者的第一交互方式是"听"
- 底部常驻**一键拨号**：不确定就打电话，这比任何帮助文档都有效
- **零跳转、零广告、零弹窗**——每一个额外的可点击元素都是认知成本

### 亮点 3 · 风险提示是一等公民，不是附加功能

每一次解读都附带内容特征判断：催办话术、个人收款码、金额异常、与实际发布者习惯不符。

家长群诈骗是**真金白银的损失**，对老年人尤其致命。把这一条做进主流程，而不是藏在二级页面，是本产品与通用摘要工具最实质的分野。

### 亮点 4 · 入口只有一个动作：转发

老人不需要：
- ❌ 学会打字提问
- ❌ 学会描述自己的需求
- ❌ 学会在对话里追问

只需要：**长按 → 转发 → 选明白卡**。这是一个他们在微信里已经做过一千次的动作。

**产品的核心竞争力是"不需要学习成本"，而不是"功能强大"。**

### 亮点 5 · 代际异步协作

把"被反复打电话问"转变为"主动看一眼"。子女端不需要安装新 App，扫码绑定即可（**不依赖微信好友关系链**——这一点很关键，小程序没有任何好友列表 API，见下方技术说明）。

## 四、差异化优势

| 现有做法 | 为什么在祖辈家长身上失效 | 明白卡的差异 |
|---|---|---|
| 微信群自带的聊天记录搜索 | 需要先想到关键词，老人在这一步就卡住 | 按**事件**归档，不靠关键词 |
| 打电话问子女 | 子女在上班；且同一件事要问很多遍 | 老人自主完成，子女异步知情 |
| 通用 AI 聊天助手 | 需要打字、需要把问题描述清楚、需要多轮追问 | 入口只有"转发"一个动作 |
| 大字版 / 关怀模式 | 只解决"看不清"，不解决"看不懂" | 解决的是**信息结构**，不是字号 |
| 家长类 App | 做的是教育内容与家校沟通，本身又是一堆新信息 | 做**信息降维**，不生产任何内容 |
| 把通知截图发给子女 | 子女看完还是要解释一遍，链路更长 | AI 直接产出可执行卡片 |

**一句话概括差异**：别人在帮用户"看得更清楚"，明白卡在帮用户"知道要干什么"。

## 五、核心定位

> **面向家庭照护场景的信息降维工具。**
> 把群消息里的书面语，降维成老人能直接执行的行动语言。

**定位边界（明确不做什么）：**

- ❌ 不是 IM —— 不替代微信，不试图把用户从群里拉走
- ❌ 不是 AI 聊天助手 —— 不要求用户提问、不提供开放式对话
- ❌ 不是家长 App —— 不生产教育内容、不做家校沟通、不碰课程与成绩
- ❌ 不是健康或医疗工具 —— 不做用药提醒、不做诊断建议（避开资质门槛）
- ✅ 是一个**极窄的工具**：通知进，行动出

**一句话电梯陈述**：

> 中国有大量正在帮子女带孩子的老人，他们每天的困扰不是不会用手机，而是看不懂家长群里的通知。明白卡只做一件事：老人把通知转发进来，它输出一张大字、能听、说清"要做什么、什么时候前、交多少钱"的卡片——并在遇到可疑收费时先拦一道。

## 六、主要功能模块

### M1 · 核心闭环（必须上线）

| 编号 | 模块 | 说明 |
|---|---|---|
| F1 | **通知接入** | 三个入口：从聊天中选择图片 `wx.chooseMessageFile`、拍照/相册 `wx.chooseMedia`、聊天工具栏入口 |
| F2 | **解构引擎** | 多模态模型读取文字与图片，按固定 JSON Schema 输出行动项、期限、金额、物品、发布者线索 |
| F3 | **行动卡渲染** | 大字排版、语音播报（TTS）、一键拨号、一屏一卡 |
| F4 | **风险提示** | 基于内容特征的启发式判断：催办话术、个人收款码、金额异常 |

**技术要点**

- **输出必须过 Schema 校验**。不合法时降级为「原文 + 语音朗读」，绝不让用户看到半成品的抽取结果。
- **不确定就说不确定**。金额、日期这类关键字段，抽取置信度低时显示原文片段让用户自己核对，不强行给结论。
- 前端：原生小程序 + TDesign；后端：微信云开发（免备案、免域名白名单，是"抢时间上线"的硬约束下的唯一合理选择）。

### M2 · 留存增强

| 编号 | 模块 | 说明 |
|---|---|---|
| F5 | **班级档案** | 按群归档通知，支持按时间回溯。优先基于群标识自动分组，不可用时降级为手动归类 |
| F6 | **代际同步** | 子女扫码绑定，异步接收父母的待办摘要 |
| F7 | **期限提醒** | 订阅消息在截止前推送。注意：一次性订阅一次授权仅能发送一条，须在生成卡片时同步请求授权 |

### M3 · 信息源扩展

| 编号 | 模块 | 说明 |
|---|---|---|
| F8 | 短信与弹窗截图解读 | 银行、快递、运营商的短信，老人同样读不懂 |
| F9 | 纸质通知拍照识别 | 学校发的纸质通知单 |
| F10 | 语音开口问 | "这条要怎么弄" |

## 七、平台能力与合规

### 7.1 依赖的微信能力（含实测状态）

| 能力 | 用途 | 状态 |
|---|---|---|
| `wx.chooseMessageFile` | 从聊天中选择图片 | 官方 API，常规能力，预期可用 |
| `wx.chooseMedia` | 拍照 / 相册 | 官方 API，需用户授权 |
| 转发消息给小程序 | 主入口之一 | ⚠️ **待实测**：转发文本消息时内容如何传递、图片是否支持 |
| 群标识 | 班级档案自动分组 | ⚠️ **待实测**：获取条件与稳定性；不可用则降级为手动归类 |
| 订阅消息 | 期限提醒 | 官方能力，模板需审核，有周期 |
| 小程序码 | 子女绑定父母 | 官方能力 |
| 聊天工具栏 | 群内快速入口 | ⚠️ **待实测**：配置要求与可用范围 |

> **明确不可用**：小程序**没有任何好友关系链 API**（`wx.getFriendCloudStorage` 是小游戏专属且仅限开放数据域）。因此代际绑定必须走"扫码 + 家庭码"，不能依赖好友列表。这一点在架构上必须提前接受。

### 7.2 合规边界

| 项 | 处理方式 |
|---|---|
| 类目 | 工具类（以微信后台实际可选类目为准，M0 核实） |
| 内容来源 | 全部由用户主动提供（转发 / 选图 / 拍照），**小程序不读取聊天记录，技术上也不可能** |
| 未成年人信息 | **不采集任何儿童个人信息**，只处理家长收到的通知 |
| AI 输出限制 | 不做医疗、法律、投资建议；不代替家长做任何付款决策 |
| 内容安全 | 接入微信内容安全检测接口 |
| 身份声明 | 产品内明确标注"风险提示基于内容特征，不构成身份认证" |

## 九、落地节奏

### 9.1 如果冲本届（10 月 17 日截止）

**必须砍到只剩 F1 + F2 + F3 三个模块的最小闭环**，F4 风险提示若时间不足可先降级为规则版。

| 日期 | 事项 |
|---|---|
| 10/8 | 报名、领 Coding Plan 资源、注册小程序主体、确认类目 |
| 10/9 | 实测三个入口的可用性，确定主入口 |
| 10/10–10/13 | 开发最小闭环（云开发 + 模型接口 + 卡片渲染） |
| **10/14** | **提交审核**（留三天缓冲改驳回） |
| 10/15–10/17 | 上线确认 + 提报材料 |

> 诚实评估：9 天完成从零到上线是极限节奏。**决定成败的是入口能否在 10/9 当天跑通**——如果三个入口都不可用，应立即放弃本届，不要硬撑。

### 9.2 如果不冲本届

把 M1 完整做完（含 F4），做一轮 ≥ 10 人的祖辈用户可用性测试，形成真实数据后再投下一年赛季或其他赛事。**一个做过用户测试的作品，在评审的"产品实用性"维度上的说服力完全不同。**

## 十、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| AI 抽取不准 | 输出错误的金额或日期，比不做更糟 | Schema 校验 + 置信度阈值 + 低置信度时展示原文核对；宁可说"没看懂" |
| 入口能力未达预期 | 核心流程走不通 | M0 立即实测，必备降级路径：截图上传（最稳） |
| 老人不愿尝试新工具 | 无法获得真实用户 | 首次配置由子女完成；对老人而言只需记住一个动作 |
| 类目不可选 | 无法上线 | M0 核实，准备备用类目 |
| 9 天工期不够 | 本届失败 | 设定放弃线（10/9 入口实测不通过即退出），把资源留给下一届 |
| 被质疑"和通用 AI 摘要没区别" | 创新性评分受损 | 答辩时用五步认知负荷对比与"零学习成本"论证，并现场演示祖辈用户测试录像 |

## 附：本方案的原创性说明

1. **问题定义是原创的**：把"祖辈家长看不懂群通知"识别为一个独立的产品问题，而非"老年人不会用手机"这个笼统命题。这是一个具体的、可验证的、此前未被产品化的认知缺口。
2. **人机分工是原创的**：不给老人一个对话框，而是把 AI 完全隐藏在"转发"这个既有动作之后。产品的竞争力来自**不做功能**。
3. **输出形态是原创的**：行动卡（做什么/何时前/带什么/交多少）这一结构，是从"老人真正需要什么"反推出来的，不是从"AI 能输出什么"正推出来的。
4. **边界是清晰且可辩护的**：不做文旅、不做游戏、不做教育内容、不做医疗建议。窄，所以做得完；也因为有取舍，所以在答辩时经得起追问。
