## 1. 调研结论汇总

调研分三类来源：**官方标准**（工信部规范、微信官方指南、国标）、**可用性研究**（Nielsen Norman Group 等）、**同类开源/产品实践**（Notally、Memori、Nabu 等）。下面按你要求的七个维度归纳。

### 1.1 字体大小

| 结论 | 具体数值 | 来源 |
|---|---|---|
| 适老版界面主要文字不小于 18 dp/pt；最大字体不小于 30 dp/pt | 18 / 30 | `[S2]` |
| 微信小程序「关怀模式」缩放倍率 1.4；iOS 关怀模式字号 23.8px，Android ×1.4 | 1.4× | `[S1]` |
| 网页端计算机适老化基础字型 ≥18px，并提供放大设置 | 18px | `[S5]` |
| 常规 App 正文 11–12px，老年用户**至少提到 16px**（+50%） | 16px | `[S16]` |
| 老年用户因视力衰退，移动端文字"太小、颜色太浅"是首要障碍 | — | `[S6]` `[S17]` |
| 实践参考：Nabu 提供 x1 / x1.5 / x2 三档字号，并在**首次启动时就问**要不要开无障碍 | 3 档 | `[S15]` |

**对本项目的含义**：18pt 是**合规下限**，不是舒适值。老人记事本的正文是"自己写的、要看清的字"，我建议正文起步 20pt（40rpx），并提供 3 档可调（详见 §6.1）。

### 1.2 对比度

| 结论 | 数值 | 来源 |
|---|---|---|
| 文本/图标等元素间对比度至少 4.5:1；字号大于 18dp/pt 时至少 3:1 | 4.5:1 / 3:1 | `[S2]` `[S12]` |
| 同上，且与 WCAG 2.1 对齐（大文本 3:1） | 同上 | `[S3]` |
| 老年群体对颜色敏感度下降，应增强对比度，**尽量避免使用蓝色** | — | `[S18]` |
| 高对比（≥4.5:1）对白内障、青光眼患者可读性提升明显 | 4.5:1 | `[S16]` |
| 浅灰文字配白底在真实光照下可读性显著下降 | — | `[S17]` |

**注意一个反直觉点**：规范允许"字号 >18pt 时降到 3:1"。**本项目不采用这个宽松档** —— 老人会在户外阳光、昏暗室内读自己写的东西，一律按 4.5:1 执行，主文本直接做到接近 7:1（AAA 级）。

### 1.3 按钮尺寸（触控热区）

| 结论 | 数值 | 来源 |
|---|---|---|
| 适老版界面主要组件可点击焦点区域 **≥60×60 dp/pt**；其他页面主要组件 ≥44×44 | 60 / 44 | `[S2]` `[S12]` |
| 单独适老版 App：首页主要组件 ≥48×48，其他 ≥44×44 | 48 / 44 | `[S2]` |
| 元素（图标、图标+文字、图片）周围加 **12pt 反馈热区**；≥44pt 且有清晰边界的元素可不加 | 12pt | `[S1]` |
| 元素间视觉距离至少 2A，热区平分间距 | — | `[S1]` |
| 按钮至少 44×44px，且界面应尽量"点击即可"，避免滑动手势 | 44px | `[S16]` |
| 触控目标至少 9mm × 9mm | 9mm | `[S16]` 引述 NN/g |
| 核心功能不应依赖双击、长按、多指手势 | — | `[S17]` |

**换算到小程序 rpx**（750rpx = 375pt，即 1pt = 2rpx）：60pt → **120rpx**，44pt → **88rpx**。

### 1.4 操作步骤与层级

| 结论 | 来源 |
|---|---|
| 老年人 95% 表现为"按部就班"（逐步思考、先看完整页再动），只有 35% 的年轻人如此 | `[S6]` |
| 中老年用户完成同一任务的效率比年轻用户低 **74%** | `[S16]` |
| 界面复杂度是主要放弃原因；简化交互可降低错误率、提升完成率 | `[S17]` |
| 扁平化原则：**不应出现 tab 页和隐藏内容**，避免阴影/透视/纹理等复杂装饰 | `[S5]` `[S2]` |
| 位置告知与纠错：应告知当前状态与位置，并提供"撤销上一步" | `[S5]` |
| 避免导航剧烈变化；一半老年人会自己记操作步骤笔记，改版会让笔记失效 | `[S6]` |
| 简化流程：减少复杂交互与特效，避免过多验证流程 | `[S12]` |
| 实践参考：Notally 极简（列表 → 编辑 → 完事），无嵌套文件夹 | `[S13]` |

**含义**：层级深度硬性限制为 **2 层**（首页 → 详情页），不用 tabBar、不用抽屉、不用长按菜单。

### 1.5 语音输入

| 结论 | 来源 |
|---|---|
| 适老化应提供语音阅读服务，并有开关控制（读屏/语音朗读） | `[S2]` `[S5]` |
| **微信「同声传译」插件（含语音转文字 ASR）不对个人主体开放**，插件类目为「IT科技 > 软件服务提供商」，个人主体无此类目 | `[S8]`（微信开放社区官方答复） |
| 社区反馈：个人主体做 ASR 只能接科大讯飞/阿里/腾讯云语音服务，**基本都需付费** | `[S8]` |
| Memori（老人日记 App）把 Speech-to-text 列为"下一步计划"，说明**未实现也不影响核心价值** | `[S14]` |
| 实践参考：Notally 也无语音输入功能 | `[S13]` |

**这是本项目最重要的一个判断**：在放弃付费 AI 订阅的前提下，**不要自建 ASR**。

**替代方案（零成本、零开发）**：引导老人使用**手机输入法自带的语音键盘**（微信聊天里他们早就会用）。小程序只做一件事——在输入区上方放一行提示：「点键盘上的话筒，说话就能变成字」。这把"语音输入"从"我们要实现的功能"变成"我们要引导的用法"，成本几乎为零，且没有识别准确率包袱。

**朗读（TTS）**：同样受 `[S8]` 的主体限制。若你的小程序是**企业/个体工商户主体**可以申请插件；若是**个人主体则不可用**，朗读功能需删除或降级为"把文字放大到最大档"。**此项需你确认主体类型**（见 §11）。

### 1.6 提醒与备份

| 结论 | 来源 |
|---|---|
| 小程序订阅消息：一次性订阅 = 用户点一次授权，只能发**一条**；长期订阅**仅限政务、医疗、交通、金融、教育等类目**，工具类基本申请不到 | `[S7]` `[S19]` |
| 授权弹窗中"总是保持以上选择"一旦被勾，后续请求会被静默忽略 | `[S7]` |
| 订阅消息定位是"服务通知"，不是营销通道 | `[S19]` |
| 小程序本地缓存：单个 key 上限 1MB，**总容量 10MB**；按小程序 + 用户双重隔离 | `[S11]` |
| 本地缓存**不跨设备**，换手机读不到，关键数据应服务端持久化 | `[S11]` |
| 云开发：可突破本地容量限制，支持同步与备份 | `[S11]` |
| 实践参考：Notally 有"自动保存与备份"、提醒、导出（PDF/TXT/JSON/HTML） | `[S13]` |
| 实践参考：MemoryCompanion、MyMemory 都以"提醒 + 任务"为核心 | `[S20]` `[S21]` |

**对"提醒"的诚实结论（重要）**：**小程序做不到像闹钟一样主动响。** 这是平台机制限制，不是实现难度问题。因此提醒必须分层设计（§7.3）：
- **主方案（100% 可靠）**：打开小程序就看见「今天要做的事」；
- **增强方案（尽力而为）**：设置提醒时顺手请求一次订阅消息授权，消耗一条额度；
- **兜底方案**：引导家人转发/提醒。

### 1.7 误触防护

| 结论 | 来源 |
|---|---|
| **可逆或后果轻微的操作不需要确认**；确认应只用于会产生后果的动作 | `[S9]`（Material Design） |
| Apple HIG 明确：**不要为常见的、可撤销的破坏性操作弹 alert**（如删邮件），应提供撤销 | `[S10]` |
| WWDC 设计原则：用 Undo 替换掉约 80% 的确认弹窗；确认只留给真正不可逆的操作（清库、销户、转账） | `[S22]` |
| 撤销应"停留足够久"，用户主动做其他操作后才消失 | `[S9]`（Snackbar with undo） |
| 适老化要求"充足操作时间"：用户操作完毕前界面不发生变化 | `[S2]` |
| 老年人手抖、精细动作能力下降，精准点击困难 | `[S18]` `[S16]` |
| 按钮文案要具体（"删除" 优于 "确定"），避免"是/否" | `[S10]` |
| 删除类操作必须有明确的取消出口 | `[S10]` `[S23]` |

**本项目做法**：删除**不弹确认框**，改为删除后首页底部出现一个**大号撤销条**（停留 10 秒，且用户做别的操作也不立即消失，而是延长到 15 秒）。理由：老人容易误触，但更容易被弹窗搞懵；撤销比确认更宽容，且不会因为"习惯性点确定"而丢数据。

## 3. 产品定位与用户

### 3.1 一句话定位

> 一个只能做一件事的记事本：**记下来，别忘了，找得到。**

### 3.2 目标用户

主用户：**60–80 岁、会用微信聊天但不太会用其他 App 的老人**。
典型场景：记孙辈放学时间、记吃药、记要去哪买东西、记儿女交代的事、记自己的血压数值。

次用户（隐含）：**子女**——帮父母装、帮父母看、偶尔代记。

### 3.3 用户画像带来的三条硬约束

1. **不会探索**：只走看得见的路。所有功能必须在首页可见，不藏在菜单/长按里 `[S6]` `[S5]`
2. **怕弄坏**：误操作后不敢再碰。必须可撤销、可找回 `[S6]` `[S9]`
3. **看不清 + 手抖**：字号、对比度、热区是生命线，不是加分项 `[S2]` `[S18]`

### 3.4 不做什么（明确剔除）

依据：扁平化、拒绝复杂装饰 `[S5]`；减少功能干扰 `[S12]`；极简实践 `[S13]`。

| 剔除项 | 理由 |
|---|---|
| 多级文件夹 / 分类管理 | 层级深、要决策，老人不会用 `[S5]` |
| 标签（tag）系统 | 同上，且增加输入负担 |
| 富文本 / Markdown / 排版工具 | 老人不需要排版，只需要字大 |

| 多指手势（双击、长按、滑动删除） | 明确禁止依赖手势 `[S17]` |
| 云同步冲突处理 UI | 单人单机使用，冲突概率极低；有冲突时静默取最新 |
| 深色模式 | 高对比浅色底对老人最友好 `[S16]`；深色模式增加维护成本，赛后再说 |

## 5. 界面布局与信息层级

### 5.1 页面结构（共 4 页，层级深度 2）

```
① 首页（列表 + 今天要做的事 + 记一条）
      │
      ├── ② 记一页 / 改一页（同一页，两种模式）
      │
      ├── ③ 看一页（详情：全文 + 改 / 删）
      │
      └── ④ 设置页（只有：字号、云端备份、关于）
```

- **不用 tabBar**：底部标签栏会让老人以为要"切换"，且占用拇指区 `[S5]`（扁平化、禁 tab 页）
- **不用抽屉、不用长按菜单、不用右滑**
- **设置入口**：首页右上角一个**文字按钮「设置」**（不是齿轮图标）——图标必须配文字 `[S12]`

### 5.2 首页布局（从上到下）

```
┌─────────────────────────────┐
│ 记得                    设置 │  ← 标题 24pt；"设置"是可点文字
├─────────────────────────────┤
│ 🔍 找一找                    │  ← 搜索框，高 88rpx
├─────────────────────────────┤
│ 今天要做的事                 │  ← 区块标题（有内容才显示）
│ ┌─────────────────────────┐ │
│ │ 下午3点 接孙女放学        │ │  ← 卡片，整块可点
│ │ 晚上8点 吃药             │ │
│ └─────────────────────────┘ │
├─────────────────────────────┤
│ 记过的                       │
│ ┌─────────────────────────┐ │
│ │ 明天上午 买降压药         │ │
│ ├─────────────────────────┤ │
│ │ 10月12日 交电费          │ │
│ └─────────────────────────┘ │
│                             │
│   ┌─────────────────────┐   │
│   │      ＋ 记一条       │   │  ← 居中超大主按钮，固定底部
│   └─────────────────────┘   │
└─────────────────────────────┘
```

布局原则及依据：

| 原则 | 说明 | 依据 |
|---|---|---|
| **主按钮在拇指区** | 「记一条」固定在屏幕底部居中，高 120rpx | 热区 ≥60pt `[S2]`；避免精准点击 `[S18]` |
| **今天要做的事置顶** | 提醒是本产品第二价值，不能藏在二级页 | 位置告知 `[S5]` |
| **一屏一件事** | 首页只有"看"和"记"，不放编辑 | 减少认知负荷 `[S17]` |
| **列表项只显示两行信息** | 首行内容 + 时间，不显示摘要、不显示字数 | 极简 `[S13]`；低效率用户 `[S16]` |
| **时间显示为口语** | 「明天下午3点」而非「2026-10-09 15:00」 | 口语直白 `[S12]` |
| **不用阴影/渐变/卡片圆角投影** | 纯色块 + 1px 边框区分 | 避免复杂装饰 `[S5]` |

### 5.3 记一页 / 改一页

```
┌─────────────────────────────┐
│ ← 返回                       │
├─────────────────────────────┤
│ 要记什么？                   │  ← 标签（不是 placeholder）
│ ┌─────────────────────────┐ │
│ │                         │ │  ← 大输入框，最小高度 400rpx
│ │                         │ │
│ └─────────────────────────┘ │
│ 💬 点键盘上的话筒，说话就能变成字 │  ← 语音引导（不自建 ASR）
├─────────────────────────────┤
│ 什么时候？（可以不填）        │
│ ┌─────────────────────────┐ │
│ │ 明天下午三点             │ │  ← 口语输入，time-parser 解析
│ └─────────────────────────┘ │
│ ┌────┐ ┌────┐ ┌────┐        │
│ │今天│ │明天│ │后天│        │  ← 三个快捷词，点了直接填
│ └────┘ └────┘ └────┘        │
├─────────────────────────────┤
│   ┌─────────────────────┐   │
│   │      记好了          │   │  ← 唯一主按钮，底部固定
│   └─────────────────────┘   │
└─────────────────────────────┘
```

关键决策：

- **标签在框外，不用 placeholder**：老人不知道 placeholder 会消失，灰色浅色文字也看不清 `[S17]`
- **时间可空**：不强制填写，降低放弃率 `[S6]`
- **三个快捷词替代日期选择器**：日期滚轮对老人是灾难；快捷词覆盖 80% 场景，剩下的靠口语解析 `[S16]`
- **语音引导而非自建 ASR**：见 §1.5 `[S8]`
- **只有一个主按钮**：不做"保存并继续""存为草稿"这类分支 `[S12]`

## 7. 简化操作的降级策略

"降级"指：**当某个能力做不到时，用更简单但同样解决问题的方案替代，而不是硬做。**

### 7.1 语音输入降级（最典型）

| 层级 | 方案 | 条件 |
|---|---|---|
| 理想 | 小程序内嵌 ASR 按钮 | 需企业主体 + 插件 + 可能付费 `[S8]` |
| **采用** | **引导使用手机输入法自带语音键盘** | 零成本、零开发、老人已在微信里会用 |
| 兜底 | 放大字号 + 加粗，降低输入难度 | 始终可用 |

具体做法：输入区下方一行提示「点键盘上的话筒，说话就能变成字」。配一个小话筒图标 + 文字 `[S12]`。

### 7.2 提醒降级（平台限制导致）

| 层级 | 方案 | 可靠性 |
|---|---|---|
| **主（P0）** | 「今天要做的事」——打开即见 | **100%** |
| 增强（P1） | 一次性订阅消息（授权 1 次发 1 条） | 低（依赖授权、依赖类目）`[S7]` `[S19]` |
| 兜底 | 详情页显示「可以把这条转发给儿女，让他们提醒你」 | 中 |
| **不做** | 假装能做到"到点自动响" | — 这是欺骗用户 |

**诚实原则**：不在 UI 里承诺"会提醒你"，只说"会记下来，打开就能看到"。若用户主动点了订阅授权，才说"到时会收到一条微信通知"。

### 7.3 备份降级

| 层级 | 方案 |
|---|---|
| 主 | 本地存储（离线可用，永远能写）`[S11]` |
| 增强 | 联网时静默同步云端，`notes` 集合「仅创建者读写」 |
| 降级 | **同步失败静默**，不弹错误。老人不需要知道同步失败了 |
| 兜底 | 设置页「从云端找回」按钮，换手机时手动恢复 |

### 7.4 搜索降级

老人输入可能有错别字、多空格。采用**宽容匹配**：忽略标点空格、逐字包含即可命中，不要求连续子串。宁可多显示几条，也不要"搜不到" `[S6]`。

### 7.5 首次启动降级（照搬 Nabu）

首次打开先问一个问题（两个大按钮）：「字要大一点吗？」「**大**」「**特大**」`[S15]`。
不做多步引导、不做功能介绍轮播 `[S5]`。

## 8. 文案规范

依据：避免专业词与新词 `[S5]`；文案口语化（"报告查询"→"查报告"）`[S12]`；用用户熟悉的语言 `[S17]`；不要居高临下 `[S17]`。

| 别这么说 | 要这么说 |
|---|---|
| 确认删除？ | 要删掉这条吗？ |
| 确定 / 取消 | 删掉 / 不删了 |
| 保存 / 提交 | 记好了 |
| 新建笔记 | 记一条 |
| 暂无数据 | 还没有记过东西 |
| 搜索 | 找一找 |
| 设置 | 设置（保留，老人认这个词） |
| 同步失败 | （不显示） |
| 提醒时间 | 什么时候 |
| 内容 | 要记什么 |
| 操作成功 | 记好了 |
| 加载中 | 正在打开… |
| 撤销 | 刚才删错了？点这里找回来 |

**三条硬规矩**：
1. 按钮文案必须是**动词短语**，不用「确定/OK/是」`[S10]`
2. 句子不超过 15 个字
3. 不用「您」（生分），用「你」

## 9. 数据模型

本地存储为主（`wx.setStorage`，总量上限 10MB `[S11]`），云端为备份镜像。

```
Note {
  id: string          // 本地生成 uuid
  content: string     // 正文，纯文本
  rawTime: string     // 用户原始口语输入，如 "明天下午三点"
  dueAt: number|null  // time-parser 解析出的时间戳；解析失败为 null
  createdAt: number
  updatedAt: number
  deleted: boolean    // 软删除，用于"找回"
}

Settings {
  fontScale: 'small' | 'large' | 'xlarge'   // 默认 large
  lastSyncAt: number
}

云端 notes 集合（镜像，权限「仅创建者读写」）
  同上字段 + _openid（云开发自动写入）
```

**关于 `time-parser.js` 复用**：它是纯函数、无 `wx.*` 依赖，可直接复制到小程序端运行，附带的 70 条语料测试也可在 Node 里跑。解析不出时间时**保留原文、不报错**——这与旧项目"低置信度降级为展示原文"的设计一致。

**不引入的东西**：状态管理库、ORM、本地数据库。10MB 对纯文本记事绰绰有余（按每条 200 字算，可存 2 万条以上）。

### 搬运 time-parser 时修掉的两个真实 bug

这两个在旧项目里也存在，只是旧项目的书面语料没覆盖到：

1. **中文数字钟点解析不出来** —— 原正则只认 `\d{1,2}`，所以「下午**三**点」匹配不到，
   `hasTime` 恒为 false。已扩展为支持中文数字并接入 `cnNumToInt()`，同时把「中午」并入下午组。
   对本项目这是致命的：老人口语里「三点」比「3点」更自然。
2. **只有钟点没有日期时完全不解析** —— 「晚上七点半吃药」这种说法没有日期词，
   `parseDeadline` 返回空。已在 `time.js` 补一层兜底：抽到钟点就默认今天，
   **若该钟点今天已过则推到明天**（依据：老人记「晚上七点半吃药」是为下一次准备，不是补记刚才）。

> 修复只改了 `apps/elder-notes/` 下的副本。旧项目 `apps/mingbaika/` 里的原件**未同步**，
> 若将来复用记得一并修。
