## 1. 发布前准备

### 1.1 代码检查与构建配置

在 `apps/elder-notes/` 下依次跑：

```bash
npm run check        # 静态自检：字号/热区/对比度/可点元素文字/标签配平
npm test             # 纯函数单测：time 29 项 + quest 49 项
```

两条都必须是绿的再上传。`npm run check` 会输出结论行"静态检查全部通过"。

**构建配置（`project.config.json`）现状与核对项：**

| 项 | 当前值 | 是否需改 | 说明 |
|---|---|---|---|
| `appid` | `wx77fb4239f60954f0` | 核对 | 与后台一致即可 |
| `miniprogramRoot` | `miniprogram/` | 不动 | ⚠️ 导入项目时要选**这一层的父目录**（`apps/elder-notes`），不能选到 `miniprogram/` |
| `setting.urlCheck` | `false` | ⚠️ 见下 | 现在是"不校验合法域名"。本项目无请求 → 无害；**但将来一旦加接口，它会让你在本地看不出域名没配白名单** |
| `setting.minified` / `minifyWXML` / `minifyWXSS` | `true` | 不动 | 压缩已开 |
| `uploadWithSourceMap` | `true` | 可选 | 便于线上排错；本项目体积远小于 2M 上限，留着无碍 |
| `packOptions.ignore` | 已排除 `node_modules` / `scripts` / `docs` / `package*.json` / `*.key` / `*.md` | 不动 | ⚠️ 密钥 `*.key` 已被排除，不会进包也不会进 git |
| `libVersion` | `latest` | 不动 | 只影响本地调试；线上由用户微信版本决定 |

建议提审前顺手做的一处改动（可选，非必须）：

- `miniprogram/sitemap.json` 现在是 `"action": "allow", "page": "*"`，即允许微信索引页面。
  本项目所有内容都在**用户本地**存储，微信索引不到任何实义内容，开了没收益；
  改成 `disallow` 可以减少"审核抓到空白页"这类不确定性。

### 1.2 接口域名：本项目**不需要配置**

已全量核查 `miniprogram/` 下所有 `.js / .wxml / .json`：

- 无 `wx.request`、无 `wx.cloud`、无 `uploadFile` / `downloadFile`
- 唯一的 `https://` 出现在 `sitemap.json` 的注释文档链接里

**结论：不需要在后台配置任何 request / socket / uploadFile 合法域名，也不需要配业务域名。**
这一节你在后台可以整个跳过 —— 别被通用教程带着去配一堆用不上的域名。

> ⚠️ **将来若加了接口**（比如云备份），必须按顺序做三件事，少一件线上必失败：
> 1. 小程序后台 **开发管理 → 开发设置 → 服务器域名** 添加 `request` 合法域名（必须 HTTPS、必须已备案域名）
> 2. 把 `project.config.json` 里的 `urlCheck` 改回 `true`，本地跑一遍确认域名没漏
> 3. 真机（非模拟器）验证，因为模拟器对域名校验较松

### 1.5 ⚠️ 示例数据（提审前必须决策）

`app.js` 的 `store.seedIfEmpty()` 会在**首次启动、本地一条记录都没有时**播种 6 条示例事件
（`miniprogram/utils/store.js` 的 `samples`）。当前示例文案：

```
量血压 / 早上起床后量一次，记下数值
吃降压药 / 早饭后一片
下楼散步 / 小区走两圈就回来
去社区医院 / 带上医保卡和上次的结果
交水电费 / 已经交了，不用再管
```

**风险**：「量血压 / 吃降压药 / 医保卡 / 社区医院」这类措辞，在审核视角里可能被归入
**医疗健康**范畴，而医疗健康类服务类目**个人主体通常不可选**、且需资质。
审核员看到首屏就是这些内容，可能会要求你改类目或补充说明。

**两个方案，需要你拍板（我没擅自改代码）：**

- **方案 A（保守，推荐）**：把示例换成不含医疗词的中性内容 ——
  「交水电费 / 买菜 / 接孙子放学 / 老同学聚会 / 给女儿打电话 / 下楼散步」。
  卖点不受影响（示例只是填充首屏），审核风险降到最低。
- **方案 B**：保留现有文案，但在提审的「补充说明」里明确写清
  "本小程序仅为个人记事工具，不提供任何医疗建议、诊疗或药品相关服务，示例内容为演示数据"。

> 另外：示例数据**不要整个删掉**。空首屏 + 4 个页面无内容，反而容易触发
> "功能不完整 / 无法体验" 的驳回。留着它，但让它中性。

### 4.4 ICP 备案：完整流程与坑（**决定 10/17 之前能不能上线**）

**结论先说**：2023-09 起，小程序**未完成备案无法提交代码审核、也无法发布上线**。
所以备案不是"发布前最后一步"，而是"提审的第一道门"。体验版不受此约束（体验版不算上架）。

**个人主体需要准备的材料：**

- 本人身份证正反面照片（边角完整、无遮挡、无反光、纯白背景）
- 本人手机号（要能收验证码，且要收工信部 12381 核验短信）
- 本人微信号，**需已绑定银行卡**（人脸核身要用）
- 精确到**门牌号**的通信地址（⚠️ 只写到某路会被驳回）

**流程（约 7–20 个工作日，首次备案可能更久）：**

1. 后台 **设置 → 基本设置 → 备案 → 去备案**
2. 填写主体信息（身份证上传后自动识别，逐字核对）
3. 填写小程序信息：名称、服务内容标识、功能介绍（20–200 字）
4. 填写负责人信息 → **人脸核身**（白墙背景，不戴帽子/眼镜反光/口罩）
5. 提交 → **微信平台初审 1–2 个工作日**（期间可能电话核实，保持畅通）
6. 初审通过 → 收到 **12381 短信 → 24 小时内**登录 `beian.miit.gov.cn` 完成核验
   ⚠️ **超时自动驳回，整套重来**，这是最常见的翻车点
7. 通管局终审 **1–20 个工作日**（普遍 7–15）→ 出备案号，自动同步到后台

**备案常见驳回（提前避开）：**

- 证件信息不一致（自动识别出错最多，逐字核对）
- 通讯地址不详细（必须到门牌号）
- 人脸核身失败（光线、帽子、眼镜反光、背景杂乱）
- 负责人手机号与微信绑定手机号不一致
- 小程序内容与所选类目不符

> 备案**全程免费**。微信认证 300 元/年是另一回事，个人主体非必须（以后台页面提示为准）。
> 备案成功后需在小程序"更多资料"中公开展示备案号。

### 4.2 服务类目怎么选（个人主体）

- 个人主体**可选类目范围比企业窄**：医疗、金融支付、新闻资讯、直播等需资质，基本选不了。
- 本项目是记事/效率工具，选类目时优先在类目选择器里搜：**工具 → 效率**、**工具 → 日程管理**、
  **工具 → 备忘录/记事**（名称以页面实际下拉项为准）。
- ⚠️ **不要为了"显得高级"选医疗健康类**。一旦类目涉及医疗，会要资质，个人主体拿不出 → 必拒。
- 类目与首页实际内容要能对上：首页是"每日任务的完成状态 + 记事"，属于工具类，不属医疗。

## 5. 常见驳回原因与规避（提审前自查）

| # | 驳回原因 | 本项目风险 | 规避 |
|---|---|---|---|
| 1 | **未备案 / 隐私保护指引未配置** | ⚠️ **高**（见 §4.1） | 后台两项都确认"已生效"再提 |
| 2 | **类目与实际内容不符 / 涉医疗资质** | ⚠️ **高**（示例数据里有降压药、医保卡） | 走 §1.5 方案 A，或不改文案也要在说明里声明（方案 B） |

| 4 | **功能过于简单 / 不完整** | 中 | 示例数据别删；补充说明写清场景；截图给首页 + 录入 + 完成态 |

## 6. 审核通过后：发布、灰度、监控、回滚

### 6.1 发布

**管理 → 版本管理** → 审核通过的版本 → **发布**。
发布时页面会给出发布方式选项（**以页面实际显示为准**）：

- **全量发布**：立即对所有用户生效
- **分阶段发布（灰度）**：按比例逐步放量（如 10% → 50% → 100%），
  任一段发现异常可**暂停**后续放量

**本项目建议**：用户量极小、纯本地应用，**直接全量发布即可**。
灰度更适合有服务端、用户量大的产品。真要稳妥，就选分阶段，先在 10% 放一天。

### 6.2 线上监控

| 手段 | 在哪看 | 本项目适用性 |
|---|---|---|
| 运维中心（错误 / 性能） | 后台 **开发管理 → 运维中心** | ✅ 能看 JS 报错、启动耗时 |
| 实时日志 | 需代码接入 `wx.getRealtimeLogManager` | ⚠️ **当前代码没有接入**。若要定位线上个案问题，我可以加（约 20 行，无网络请求也能用） |
| 客服 / 意见反馈 | 后台 **客服** 模块 | 建议配置，审核也常看有没有反馈渠道 |
| 用户投诉 | 后台 **管理 → 用户反馈** | 有反馈要尽快处理，长期不处理会影响后续审核 |

### 6.3 异常回滚

⚠️ **最重要的一条认知：小程序没有热更新。** 线上代码改一个字也要重新提审 → 审核 → 发布。
所以"提审前自查"必须严格，别指望上线后快速修。

回滚手段（按优先级）：

1. **分阶段发布暂停**：如果用的是灰度，直接暂停放量，未覆盖到的用户不受影响
2. **版本回退**：后台版本管理 → 线上版本 → **版本回退**。
   ⚠️ 通常只能回退到**上一个**线上版本，不是任意版本；回退后旧版本即为用户可见版本
3. **紧急下线**：后台可操作将小程序临时下线（慎用，所有人都打不开）
4. **重新发版**：修好代码重新上传提审（最快也要 1 个工作日）
