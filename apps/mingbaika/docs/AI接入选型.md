# 明白卡 · AI 解析接入选型

> 状态：v1.0 决策备忘 | 2026-10-08
> 用途：回答「后端调哪个模型、怎么调」。结论先行，依据在后。
> 标注约定：凡未实测的一律写「待实测」，不当结论用。

---

## 〇、结论

**默认走「云开发托管」路线（`cloudbase`）。**

不是因为它更便宜，而是因为这个产品的输入**主要是图片**：

老人从群里转发过来的往往是截图或照片。云开发托管的 AI 能力**原生支持图片输入**（官方 API 里 `content` 是数组，可放 `{ type: 'image', image_base64: ... }`），一步就能把「读图 → 理解 → 结构化」做完。

而 DeepSeek 官方 API 目前的主力是**文本模型**。走直连路线就必须自己补一个视觉环节（换成 VL 模型，或先 OCR 再喂文本），多一段链路、多一个失败点。

代码层面两条路线**都已经实现好了**，`config.js` 里改一个值就能切换。

---

## 一、两条路线

| | 路线 A：云开发托管 | 路线 B：HTTP 直连 |
|---|---|---|
| 调用方式 | 云函数内 `cloud.extend.AI.createModel()` | 云函数内 `https.request` 打厂商 API |
| 实现文件 | `providers/cloudbase-ai.js` | `providers/http-deepseek.js` |
| 配置开关 | `AI_PROVIDER=cloudbase` | `AI_PROVIDER=http` |
| API Key | **不需要**，平台托管 | 需要，放云函数环境变量 |
| 可选模型 | 云开发售卖的模型：`deepseek-v4-flash`、`deepseek-v4-pro`、`glm-5.1`、`kimi-k2.6`、`minimax-m2.7`、`hy3-preview` | 任何 OpenAI 兼容协议的模型 |

---

## 二、八个维度对比

| 维度 | 路线 A 云开发托管 | 路线 B HTTP 直连 |
|---|---|---|
| **图片输入** | ✅ 原生支持，无需额外环节 | ⚠️ 取决于模型；DeepSeek 主力模型不支持，需换 VL 或加 OCR |
| **密钥管理** | 平台托管，不落代码与环境变量 | 自管，需写进云函数环境变量并注意轮换 |
| **接入复杂度** | 低（云函数里三行） | 中（请求构造、超时、重试、厂商差异） |
| **域名白名单** | 不涉及 | 不涉及（云函数出网不受小程序白名单限制） |
| **成本可见性** | 走云开发套餐/资源包，控制台看用量 | 厂商账单，单价透明 |
| **模型可控性** | 只能用平台上架的 | 完全自由，可钉版本、可换厂商 |
| **换模型成本** | 改 `AI_MODEL` 字符串 | 可能还要改请求体格式 |
| **额度来源** | 云开发套餐 / 资源包 | 可用大赛发放的 API 额度 |

> 说明：小程序端能否**直连**模型（不经云函数）？技术上可以（`wx.cloud.extend.AI` 在基础库 3.7.1+ 可用）。但**本项目刻意不用**——因为 Schema 校验、降级判定、幂等、风险规则全在云函数侧的 `core/` 里，前端直连会让这些兜底逻辑失去位置。宁可多一跳。

## 三、成本量级（估算，非报价）

不给具体金额，因为 `deepseek-v4-flash` 的实时单价需要以云开发控制台/厂商定价页为准，我不能凭记忆编。

只给**用量量级**，方便你换算：

| 项 | 单次量级 |
|---|---|
| 输入（一段 300 字通知 + 1 张截图） | 约 1,000–2,500 token（含图片编码） |
| 输出（结构化 JSON） | 约 400–800 token |
| 单次合计 | 约 1,500–3,300 token |

换算方法：**单次成本 ≈ 上述 token 数 × 该模型单价**。测试期跑 1,000 条通知，按上限估就是约 330 万 token。

⚠️ **一条需要你自己核实的权益**：搜索结果显示云开发曾有过「每个环境赠送 100 万 token」的限时活动，但页面写明**截止时间为 2025 年 12 月 31 日**——现在已经过期。**当前是否还有赠送、额度多少，必须去云开发控制台的 AI+ 页面确认**，我不能替你断言。

## 四、什么时候该切到路线 B

出现下面任一情况，切 `AI_PROVIDER=http`：

1. **云开发的图片解析效果不达标** —— 通知截图往往有排版、表格、手写体，如果 `deepseek-v4-flash` 读不准，换成视觉能力更强的模型（把 `AI_MODEL` 和 `AI_HTTP_BASE_URL` 指过去，`http-deepseek.js` 不用改）。
2. **成本失控** —— 直连能拿厂商的阶梯价或大赛额度。
3. **需要钉死模型版本** —— 答辩演示前不希望模型被平台悄悄升级导致效果漂移。

切换只需要在云函数的环境变量里设三项：

```
AI_PROVIDER = http
AI_HTTP_BASE_URL = https://api.deepseek.com/v1
AI_HTTP_API_KEY = sk-xxxxx
```

## 五、待实测项（这几条我没有验证过，不算结论）

| 编号 | 事项 | 为什么重要 | 怎么验证 |
|---|---|---|---|
| V1 | **云函数侧 `cloud.extend.AI` 是否真的可用** | 这是路线 A 的地基。微信官方文档只写了**小程序端**的用法，云函数端只有社区示例，且社区里有人发帖说「`cloud.extend` 找不到 AI」 | 部署一个最小云函数，`console.log(typeof cloud.extend?.AI)`，看是否 `object` |
| V2 | **`generateText` 的参数形态** | 文档写 `{ data: {...} }`，社区示例写裸 `{...}`。两者不一致 | 代码已做「两种都试」的兼容，实测确认哪种生效后可以删掉另一条 |
| V3 | **图片输入是否真的支持 `deepseek-v4-flash`** | 多模态能力可能只在部分模型上开放。社区示例用的是 `hunyuan` 系列 | 用一张真实通知截图跑一次，看能否读出文字 |
| V4 | **单张图片大小上限** | 代码里设了 5MB 硬闸，但平台真实上限未知 | 逐步加大图片测试 |
| V5 | **云函数超时上限** | 配置写了 60s。图片解析可能慢 | 控制台看是否被限制到更低值 |

## 六、和纯函数内核的关系（重要）

两条路线都只负责**把模型的原话拿回来**，不做任何判断。真正的规范化、校验、日期计算、风险判定、降级，全在 `core/` 里：

```
providers/*  →  返回一段文本
                    ↓
            core/json-extract  →  抽出 JSON
                    ↓
            core/pipeline      →  规范化 → 校验 → 本地重算日期 → 风险 → 降级
                    ↓
                 最终卡片
```

这样设计的直接好处是：**换模型不影响任何业务逻辑**，而且 `core/` 那 46 项测试在切模型后依然有效——它们跑的是纯函数，不碰网络。

---

## 七、我的推荐

**先按默认（云开发托管）跑通，把 V1–V3 实测掉。**

- 实测通过 → 就用它，本阶段不再折腾。省下的时间花在入口实测和用户测试上，那才是这个赛事真正的胜负手。
- V1 或 V3 不通过 → 切到路线 B，改环境变量即可，代码不用动。

不要在第 2 天就开始纠结模型选型。**入口能不能跑通（三个通知入口）比模型选型重要一个数量级**——入口不通，模型再好也没用。
