# 明白卡 · 纯本地技术方案（去 AI 依赖）

> 制定日期：2026-10-08  
> 触发原因：云开发托管 AI 通道无可用订阅额度/套餐，第三方 AI 调用不可作为主链路依赖。
>
> **核心结论：这不是推倒重来。现有内核约 60% 可直接复用。**

---

## 0. 先说结论

| 问题         | 答案                                                                                                                 |
| ---------- | ------------------------------------------------------------------------------------------------------------------ |
| 要重写多少？     | **不多**。`core/` 共 1193 行，其中 `time-parser.js`(348) + `risk-rules.js`(178) + `schema.js`(345) 本来就**不依赖 AI**，可直接搬到小程序端 |
| 真正要新写什么？   | 从文本抽「行动项 / 金额 / 携带物 / 地点 / 标题」——约 300–500 行规则代码                                                                    |
| 数据契约改吗？    | **一个字不改**。ActionCard Schema 保持 v1.0                                                                                |
| 图片还能识别吗？   | **不能**（本地没有可用的 OCR）。改为借微信自带的「长按图片→提取文字」，见 §5.2                                                                     |
| 将来有额度了怎么办？ | 换掉一个 provider 即可，其余不动（§4.3 专门为此设计）                                                                                 |

---

## 1. 为什么必须放弃 AI 依赖（现状事实）

- 云开发控制台 → AI → 生文模型列表里**全是混元系**（hy3 / hy4-preview / hy-vision 等），  
  原配置的 `deepseek-v4-flash` **不在这个通道里**（2026-10-08 截图证实）
- 该列表所有模型**状态开关均为关闭**，且无可用订阅额度/套餐
- 结果：每一次解析都必然失败 → 全部降级成「这条我没看懂」

**这不是"暂时不通"，是架构依赖不成立。** 继续依赖一个不可用且计费的外部服务，  
对一个要拿去参赛、要给老人用的产品来说，风险不可接受。

---

## 2. 新技术栈与选型理由

### 2.1 总体选型

| 层      | 选择                                                 | 理由                                |
| ------ | -------------------------------------------------- | --------------------------------- |
| 小程序框架  | **原生 WXML/WXSS/JS**（不变）                            | 已跑通，无迁移成本；不引入 Taro/uni-app 等额外构建链 |
| 解析引擎   | **纯 JS 规则引擎（正则 + 词典 + 启发式）**，跑在**小程序端**            | 见下                                |
| 中文分词   | **不引入分词库**，用领域词典 + 正则                              | 通知文本句式高度固定，分词库（几十 KB–几 MB）是过度设计   |
| 存储     | 本地 `wx.setStorageSync`（不变）；云端保留但**降级为可选**          | 核心链路零网络依赖                         |
| 云函数    | **默认不调用**。保留 `parseNotice` 及 `core/`，作为将来接回 AI 的资产 | 见 §4.3                            |
| 语音 TTS | **保留**微信同声传译插件                                     | 微信官方免费能力，非计费 AI 订阅；且是本项目核心价值之一    |

### 2.2 为什么规则引擎跑在**小程序端**而不是云函数

| 维度   | 端上（选这个）                  | 云函数          |
| ---- | ------------------------ | ------------ |
| 离线可用 | ✅ 弱网/无网也能解析              | ❌ 必须联网       |
| 成本   | ✅ 零                      | 消耗云资源额度      |
| 响应速度 | ✅ 毫秒级                    | 秒级（冷启动 + 网络） |
| 老人场景 | ✅ 电梯/地铁/乡下都能用            | ❌ 弱网即失败      |
| 将来混用 | ✅ 端上先跑规则，失败再上云调 AI（天然分层） | 只能二选一        |

**这是本方案最重要的一个决策**：把解析放到端上，不只是为了省钱，  
更是让产品在**弱网环境**下真正可用——这正是老人使用场景的常态。

### 2.3 为什么不引入本地 OCR / 端上小模型

| 方案                      | 否决理由                                 |
| ----------------------- | ------------------------------------ |
| Tesseract.js 等 wasm OCR | 包体积数 MB，主包 2MB 限制装不下；小程序环境兼容性与性能均不乐观 |
| 端上小模型（ONNX Runtime 等）   | 同样受包体积与算力约束；且需要模型文件，本质仍是"模型依赖"       |
| 微信 OCR 插件               | 需单独申请且多为付费能力，与"不依赖计费服务"的前提冲突         |

**结论：图片识别这条路在本阶段彻底放弃，改为借力微信已有能力（§5.2）。**

## 3. 整体架构

```
┌─────────────────────────────────────────────────────────┐
│  小程序端（全部离线可用）                                  │
│                                                          │
│  输入层                                                   │
│   ├ 粘贴/输入文字   ← 主入口（新增）                       │
│   ├ 微信分享转发进来（rawText）                            │
│   └ 图片入口        ← 降级：只引导提取文字，不做识别        │
│                          ↓                                │
│  engine/  本地解析引擎（新增，纯函数，可单测）               │
│   ├ extract/  抽取器：时间·金额·行动项·携带物·地点·发布者    │
│   ├ risk/     风险规则（复用现有 risk-rules.js）           │
│   ├ schema.js ActionCard 契约（复用现有，不改）             │
│   └ parse.js  主入口 → 产出「与 AI 输出同构」的 JSON        │
│                          ↓                                │
│  pipeline.buildActionCard()  ← 复用现有，不改               │
│   （规范化 / 边界裁剪 / 置信度 / 降级判定）                  │
│                          ↓                                │
│  ActionCard（Schema v1.0，契约不变）                       │
│                          ↓                                │
│  展示层：结果页大字卡 / 朗读 / 拨号 / 历史                  │
└─────────────────────────────────────────────────────────┘

  云函数 parseNotice  —— 默认不调用；保留为将来接回 AI 的替换点
```

### 3.1 关键设计：本地抽取器产出「与 AI 同构」的 JSON

这是整个方案能低成本落地的**核心技巧**：

```
AI 路线     ：文本 ──AI──> {title, summary, items[], risks[], confidence} ──┐
本地路线（新）：文本 ──规则─> {title, summary, items[], risks[], confidence} ──┤
                                                                           ↓
                                              同一个 buildActionCard() 处理
                                                                           ↓
                                                          ActionCard（完全一致）
```

两条路线的**中间产物结构相同**，因此：

- `pipeline.js` / `schema.js` / `fallback.js` **一行不用改**
- 前端渲染代码**一行不用改**
- 116 条既有单测**继续有效**
- 将来换回 AI，只需把「本地抽取器」换成「AI 调用」，下游全不动


## 5. 功能处置清单

### 5.1 保留（不动）

| 功能                     | 说明                                              |
| ---------------------- | ----------------------------------------------- |
| ActionCard Schema v1.0 | 契约不变，这是整个复用设计的基础                                |
| 时间/期限解析                | `time-parser.js` 348 行 + 70 条语料，**直接搬**         |
| 风险识别 5 类规则             | `risk-rules.js` 178 行，**直接搬**。关键词/正则即可，本来也不靠 AI |
| 降级机制                   | 低置信度 → 展示原文 + 朗读。**本地方案下更重要**，见 §7              |
| 置信度与原文并列展示             | 规则抽取不确定性更高，这个机制从"保险"变成"必需"                      |
| 历史（本地 50 条）            | 本来就离线                                           |
| 语音朗读 TTS               | 微信官方免费插件能力，保留                                   |
| 幂等 requestId           | 端上同样需要（防连点）                                     |

### 5.2 降级

| 功能                 | 原方案               | 新方案                                                |
| ------------------ | ----------------- | -------------------------------------------------- |
| **图片识别**           | 上传云存储 → AI 视觉模型读图 | **移除**。改为引导用户：**微信里长按通知图片 → 「提取文字」 → 复制 → 粘贴进明白卡** |
| 聊天素材入口（scene 1173） | 传图给 AI            | 保留入口，但仅接受**文本**转发；图片素材给出"请先提取文字"的引导                |
| 拍照/相册入口            | AI 识图             | 保留按钮但改文案为「拍照后提取文字」；或直接隐藏（待你定，见 §8）                 |
| 置信度来源              | 模型自评              | 改为**规则命中推导**：命中字段数 / 关键词强度 / 时间可解析性 → 打分           |

**关于图片降级的说明（重要）**：这不是敷衍。  
微信客户端自带的「长按图片 → 提取文字」本身就是成熟的 OCR 能力，  
**免费、无需接入、识别质量比我们自己接任何服务都稳**。  
我们要做的只是把用户引导到这条路上，产品价值并不损失。

## 7. 风险与兜底（重要）

### R1 · 规则引擎覆盖率必然低于 AI

这是**必须接受的代价**，不是缺陷。兜底三层：

1. **降级机制（已有）**：置信度不足 → 不硬凹，直接展示原文 + 朗读 + 引导打电话
2. **原文永远可见**：任何抽取结果都可以对照原文核对（现有设计已支持）
3. **诚实标注来源**：卡片上标明"按规则识别，请核对"，不误导用户以为很准

> 对老人场景而言，**"明确告诉你我没看懂"远好过"给你一个可能错的结果"**。  
> 这一点现有降级设计已经做对了，本地方案只是让它更频繁地被触发。

### R2 · 中文通知的表达极其多样

应对：**语料驱动开发**。先收集 50+ 条真实家长群通知（你手头应该有），  
写成测试用例，逐条调规则。**不要凭空写正则**。

这是 S7 单独列一步的原因——**没有语料，规则引擎就是闭眼开车**。

### R3 · 分句与行动项切分是最大难点

"请于10月15日前交秋游费120元，并带水壶和帽子" → 应该切出几条行动项？

建议：**先做保守切分**（整句作为一个行动项），准确率优先于粒度。  
宁可给出 1 条完整信息，也不要切成 3 条错的。粒度优化放到赛后。

### R4 · 图片入口改动影响既有使用习惯

用户已被教育过"从聊天选图片"。改文案需要明确引导，否则老人会困惑。  
建议在图片入口点击后，直接弹一个**图示步骤**：长按图 → 提取文字 → 复制 → 回来粘贴。

## 8. 需要你决定的两件事

1. **拍照/相册入口**：保留（改成引导提取文字）还是**直接隐藏**？
   - 保留：入口多、老人可能困惑，但未来接回 AI 时不用重新加
   - 隐藏：首页更干净，主入口（粘贴文字）更突出
   - **我的建议：先隐藏**。主入口突出，等 AI 回来再放开。
2. **能否提供真实通知语料？** 这是 R2 的关键。  
   你手头（或家里群里的）真实通知，脱敏后给我 20–50 条，  
   规则引擎的准确率完全取决于这个。没有它我只能凭空写正则，效果没保证。

## 附：本方案刻意不做的事

- ❌ 不引入任何第三方 AI / OCR 服务
- ❌ 不改动 ActionCard Schema（这是复用的基石）
- ❌ 不做端上机器学习/小模型（包体积与算力不允许）
- ❌ 不重写已稳定的时间解析与风险规则（直接搬）
- ❌ 不在本阶段追求行动项细粒度切分（准确率优先）
