  A5 庭院装扮、A6 配置管理后台（§4.6 只说"走配置表"，没说谁改怎么改）、A7 埋点与数据看板、
  A8 被分享者落地页、A9 运营位/公告/客服入口、A10 错误监控。

  与 `count` 字段矛盾等）与 **C 类 9 项本期明确不做**（防范围蔓延）。
- **三项架构铁律**（写入文档 §3.1，后续 code review 依据）：
  1. 视图层不得算数（WXML 里出现算术表达式即拒）；2. `core/` 不得 import `wx.*`
  （保证可 Jest 直测 + 可整体迁移小游戏）；3. 前端不得产生权威数据。
- **数据所有权矩阵**：每个集合只允许**一个写者**，全部写操作走云函数，库权限设"仅管理端可写"；
  唯一例外是 `users.settings`（本地优先，异步同步）。
- **关键技术落地方案（附可机械复现的验收）**：
  - §4.1 确定性随机：改用 **xorshift32 + FNV-1a 32 位**（不用 `Math.random`，只用整数位运算，
    可移植到遇光 Java 端）；**`salt` 必须落库**否则无法事后审计；加权抽取函数三端共用、
    随机数消费顺序即协议。验收 = 同 seed 跑 1000 个随机数取 SHA256，Node 与云函数两端必须一致。
  - §4.2 时间权威：`offset = serverTime − Date.now()` 校正，全部走 `clock.now()`，
    用 ESLint `no-restricted-globals` 拦截裸 `Date.now()`。
  - §4.3 状态机：**状态由事实推导，不作为独立字段存储**；`SETTLING` 必须由服务端
    `settled === false` 决定而非时间推导（离线期间该状态必须保留）；`PACKING` 不落库（纯过场动画）。
  - §4.4 幂等：**用 `requestId` 构造确定性 `_id`**（`${openid}_${requestId}`），撞 `_id` 即幂等返回；
    事务内先 `doc().get()` 判断标记再写。**注意云开发事务内一般不支持 `where` 查询**，
    故写路径必须设计成"能按 `_id` 定位"的形状 —— 此项列入 M0-T05 实测确认。
  - §4.5 配置热更新：版本号比对 + 单文档建议 <128KB 超出则分区 + `assetsVersion` 同时驱动
    图片 CDN 路径 + 前端 schema 校验 + 本地兜底 JSON。
  - §4.6 分包：主包 ≤1.5MB；**分享落地页做成独立分包**（`independent: true`，
    被分享者无需下载主包，是分享转化率的关键）；图片一律不进包。
  - §4.7 渲染：**默认 WebView + TDesign**，Skyline 只在 M5 对「庭院」单页灰度评估（不冒进迁移）。
  - §4.8 订阅消息：一次性订阅**一次授权只能发一条**，故要在"送出门成功后"与"结算完成时"
    两个高意愿时点反复请求；模板 ID 有审核周期 → M0 就申请。
  - §4.9 手绘地图：真实底图合规成本高且与画风冲突 → 图鉴地图用**手绘插画 + 百分比锚点**，

## 载体选型核数（回答"小程序游戏用什么开发"）

- 交付 `docs/闽游蛙-载体选型备忘.md`（v1.0），作为实施计划 **D1** 的决策依据留档。
- **核心结论**：默认走**路线 A · 微信小程序（原生框架 + TDesign）**。理由不是"小程序更好"，
  而是**产品形态与两条路线的能力错配**：闽游蛙 90% 工作量在 UI（列表/卡片/弹窗/图文排版），
  且状态推进靠**时间戳解锁**而非帧循环，Canvas 的核心优势完全用不上；用游戏引擎等于先重写一套 UI 框架。
- **本次核实的平台限制（官方来源，非凭记忆）**：
  | 项 | 小程序 | 小游戏 |
  |---|---|---|
  | 主包/单包 | **2MB** | 主包 **4MB** |
  | 总量 | 所有分包合计 **30MB**（服务商代开发 20MB） | 主包+分包合计 **20MB** |
  | 渲染 | WXML/WXSS | **Canvas 全自绘，无 DOM/HTML/WXML** |
  | 类目 | 可自选 | 一级类目**锁定"游戏"不可改** |
  | 好友链 | **完全无 API** | 开放数据域内可用 `wx.getFriendCloudStorage` |
  - 来源：微信开放文档《分包加载》、腾讯云《小游戏分包加载》、微信开放文档小游戏 API 页。
- ⚠️ **修正了上一版实施计划的一个事实错误**：原写"小程序总包 20MB"，实为 **30MB**。
  已改实施计划 §4.6 的问题描述与验收断言（总包 20MB → 所有分包合计 30MB）。
- **确认了 A2 技术空白的成因**：`wx.getFriendCloudStorage` 是**小游戏专属**且**只在开放数据域可用**
  （需 `scope.WxFriendInteraction` 授权，基础库 1.9.92+），普通小程序**没有任何等价 API**。
  → 闽游蛙好友系统只能走"分享互加 + 蛙友码"，社交冷启动会慢；缓解方案见备忘 §4.1。

  LayaAir（轻量，核心约 300KB）、Unity+转换 SDK（只适合移植已有项目）、团结引擎（微信为原生构建目标）、
  裸 Canvas/weapp-adapter、Egret（社区萎缩，新项目不建议）。
  另记录了**待复核项**：有第三方资料称 Cocos 引擎运行时自微信客户端 7.0.7 起内置为微信 App 插件

## 第三条产品线立项：明白卡（参赛项目方案）

- 交付 `docs/参赛项目-明白卡-方案.md`（v1.0），为 2026 微信小程序开发大赛专门设计。
- **硬约束回顾**：用户要求新方向必须与遇光、闽游蛙**完全不重叠**。已按
  **赛道 / 核心用户 / 使用场景 / 数据对象** 四个维度论证零重叠（见文档 §0）。
  遇光占文旅，闽游蛙占游戏，明白卡占**信息无障碍 / 家庭照护工具**。
  唯一共用物是工程基建（云开发、TDesign），不含任何业务逻辑与数据模型。
- **产品定义**：面向隔代照护的祖辈家长（55–75 岁），把家长群里的通知
  **解构成行动卡**（做什么 / 何时前 / 交多少 / 带什么 / 有没有风险），
  大字排版 + 语音播报 + 一键拨号；入口只有一个动作——**长按转发**。
- **核心洞察（本方案的立论基石）**：数字鸿沟的真正形态不是"不会用手机"，
  而是"群消息里的书面语看不懂"。老人操作层没问题（会发语音、会抢红包），
  卡在**信息层**——无法从长通知里提取行动项。这个缺口此前未被产品化。
- **差异化立论**：别人帮用户"看得更清楚"，明白卡帮用户"知道要干什么"。
  对比对象包括：微信聊天记录搜索（依赖关键词）、通用 AI 助手（依赖会提问）、
  大字版/关怀模式（只解决看不清）、家长类 App（只生产更多信息）。
- **风险提示是一等公民**：家长群冒充老师收费是真实案件高发区；
  每次解读都做基于内容特征的启发式判断（催办话术 / 个人收款码 / 金额异常）。
  ⚠️ 文档中明确声明：这是**内容特征判断，不是身份认证**——小程序读不到聊天记录，
  也无法验证群成员身份，这条边界不能含糊。
- **已知平台约束（已写入文档并标注实测状态）**：
  - `wx.chooseMessageFile`（从聊天选图）、`wx.chooseMedia`（拍照）为常规能力；
  - **转发消息给小程序的内容传递方式、群标识、聊天工具栏三项均标为「待实测」**，
    不作为结论使用；主入口若全部失效则降级为"截图上传"（最稳）。
  - **小程序仍无好友关系链 API**（与 A2 结论一致）→ 代际绑定只能走"扫码 + 家庭码"。
  - 订阅消息一次性授权一次只能发一条 → 须在生成卡片时同步请求（与闽游蛙 §4.8 同结论）。

### 新增：面向零基础用户的教程 `apps/mingbaika/docs/部署指南-小白版.md`

用户说明自己"是小白，一步步说清楚，先不管时间"。原《部署指南.md》是**工程视角**
（术语密、以"为什么"和排错为主），对第一次做小程序的人门槛过高，故另写一份**操作视角**教程。
两份文档的分工：工程版答"为什么/卡在哪"，小白版只答"点哪里、看到什么算成功"。

设计上刻意做的四件事：
1. 开头先破最大的困惑：**网页后台（mp.weixin.qq.com）** 与 **开发者工具（桌面软件）**
   是两个不同的地方，之后每步都标明在哪个地方做。
2. 三个核心名词先给"长什么样 + 从哪来"（AppID / 环境 ID / 上传密钥），避免被术语击穿。
3. 8 步，每步含「在哪做 / 点哪里 / 成功标志 / 报错怎么办」。
4. 明确"能测试"与"要上架"的分界：**第 6 步做完即可在手机上演示**（体验版免备案）；
   第 7–8 步（备案、提审）只影响"陌生人能否搜到"，不阻塞开发与测试。

内容事实全部继承已核实结论（ICP 备案强制、体验版免备案、隐私协议必须先配），未新增未经验证的说法。
